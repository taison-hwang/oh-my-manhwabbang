# 00 — 작업 크기, 오케스트레이션, 작업 분리

## 절차는 작업 크기를 따른다 (기본 지침)

티어 표와 전량 절차의 원본은 `docs/HANDOFF.md` §7.0·§7.1이다. 여기는 세션마다 지켜야 할 핵심만 둔다.

- **작업을 시작할 때 티어를 한 줄로 말한다.** 사용자가 싸게 올리거나 내릴 수 있게 하기 위해서다.
- T0(오타·문구·상수 하나)는 고치고 끝. T1(한 파일, 기존 패턴, 새 동작 없음)은 직접 구현 + 그 파일 테스트 + 게이트 하나.
  T2(여러 파일 또는 두 계층, 사용자에게 보이는 동작 변경)는 구현 + 별도 에이전트 리뷰 1회 + 관련 게이트.
  T3는 전량 절차 — 이 파일의 위임·병렬 원칙과 `20-review-cycle.md` 전부.
- **T3 트리거는 크기와 무관하다.** 하나라도 참이면 T3다: 와이어 계약·골든·스키마·마이그레이션이 움직인다 /
  `docs/decisions.md`에 판정이 필요하다 / 출하된 결함을 고친다 / 저장 계층에 쓴다 / 삭제·권한·인증.
  눈대중으로 넘기지 말고 매번 다섯 개를 실제로 훑는다.
- **판단이 서지 않으면 한 단계 올린다. 내리는 것은 사용자만 한다.**

## 오케스트레이터는 지휘만 한다 (T3에서 적극 적용)

오케스트레이터(메인 세션)의 컨텍스트는 **희소 자원**이다. 컨텍스트 고갈은 이 프로젝트의 주된 실패 모드다.

- **실행은 위임하고, 오케스트레이터는 결론만 보유한다.**
- 파일 전문 읽기, 대량 grep, 로그 스캔, 반복 편집 같은 "부피 큰 작업"은 서브에이전트에 맡긴다.
  코드 위치 찾기는 graft(`graft ask`/`grep`/`callers`)를 먼저 쓴다.
- 서브에이전트에게는 **압축된 결론**을 요구한다. 파일 내용 붙여넣기 금지, 필요한 것은
  `file_path:line` 참조 + 판단에 필요한 최소 근거. 에이전트 사이에는 내용이 아니라 **경로**를 넘긴다.
- 여러 작업이 서로 독립이면 **한 메시지에서 동시 호출**해 병렬 실행한다.

### 위임하지 않는 예외

- 이미 컨텍스트에 있는 파일의 한두 줄 수정
- 경로·심볼·값이 특정된 단건 조회
- 사용자와의 대화·확인·질문
- 이미 전문이 컨텍스트에 있는 내용의 재구성 — 위임해도 원문을 다시 넘겨야 하므로 절약 효과가 없다

## 작업 분리 단위

위임 단위는 **"독립적으로 검증 가능한 결과물 하나"**를 기준으로 자른다.

- 좋은 단위: "D-73 장별 디렉터리 분할을 스캐너에 구현 + 테스트 통과", "`arch-backend.md` §7 계약 대비 핸들러 누락 목록"
- 나쁜 단위: "프로젝트 전체 처리"(너무 큼), "import 한 줄 추가"(너무 작음)

각 서브에이전트 프롬프트에는 반드시 포함한다:

1. 목표와 완료 조건(Definition of Done)
2. 건드릴 범위 / 건드리면 안 되는 범위 — **파일 목록으로**
3. 반환 형식(요약 길이, 필요한 필드)

## 병렬 실행

- 병렬 에이전트마다 **자기 파일 목록·자기 스크래치 디렉터리·자기 포트·자기 출력 경로**를 준다.
- 저장소에 부산물을 남기지 말라고 명시한다. 작업 트리 규칙은 `50-environment.md`를 따른다.

## 비상 정지

같은 종류의 오류·동작이 **5회 연속** 반복되면 멈추고 사용자에게 알린다.
