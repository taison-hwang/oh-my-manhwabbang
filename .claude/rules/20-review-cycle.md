# 20 — 구현 → 리뷰 → 개선 사이클 (필수)

**적용 범위는 티어를 따른다**(`00-orchestration.md`). T0·T1은 리뷰 없이 구현과 게이트로 끝난다.
T2는 아래 사이클을 리뷰 라운드 1회로 돌린다. T3는 전부 적용하고, 수정 적용도 구현자가 아닌 에이전트가 한다(HANDOFF §7.1).

## 1. 구현

- `10-model-routing.md` 기준으로 `opus` 서브에이전트에 위임하고, TDD로 진행한다(`15-tdd.md`).
- 완료 시 서브에이전트는 **변경 요약 + 변경 파일 목록 + 자체 검증 결과(실행한 게이트와 출력)** 를 반환한다.
- 검증 없이 "완료"라고 보고하지 않는다. 실행한 명령과 출력이 근거다.

**게이트는 티어가 아니라 건드린 것을 따른다.** 다섯 전부(`make gates`)는 T3와 커밋 직전에만 돌린다.

| 건드린 것 | 게이트 |
| --- | --- |
| Go 코드 (`internal/`, `cmd/`, `scripts/*.go`) | `make lint` + `make test` |
| 웹 (`web/src`) | `make web-gates` (typecheck · lint · test · build) |
| HTTP 응답·스캔 결과처럼 서버 밖에서 보이는 동작 | 위에 더해 `make e2e-synthetic` — 실 컬렉션 라운드는 `make e2e` |
| T3 · 커밋 직전 | `make gates` (다섯 전부) |

## 2. 리뷰 — 한 사이클에 리뷰 라운드는 **한 번**

> 이 절이 **리뷰 실행자 선택의 규범 원본**이다. 다른 파일은 이 절을 링크만 하고 다시 서술하지 않는다.

**용어:** **리뷰 라운드 1회** = 한 사이클에서 그 변경분을 훑는 리뷰 한 벌. 다관점 fan-out으로
관점을 나눠 여러 번 호출해도 **그 전체가 라운드 1회**다.

리뷰 실행자는 아래 둘 중 **하나만 고른다(택일).** 선택은 **라운드 시작 시 한 번** 하며, 관점마다 다시 고르지 않는다.

| 조건 | 리뷰 실행자 |
| --- | --- |
| `command -v codex` 성공 | **codex** — 외부 관점 |
| codex 미설치 / 인증 실패 / 반복 타임아웃 | **오케스트레이터와 동일 모델의 리뷰 전용 서브에이전트** — 내부 폴백 |

codex를 우선하는 이유는 자기 코드를 자기가 리뷰하는 편향을 피하기 위한 외부 관점 확보다.
어느 쪽이든 **구현자와 리뷰어는 다른 에이전트**다.

**금지:** codex 리뷰를 마친 뒤 같은 라운드에서 내부 리뷰 서브에이전트를 **추가로 띄우지 않는다**(이중 리뷰).
라운드를 내부 폴백으로 시작했다면 같은 라운드에서 codex로 되돌아가지 않는다.

**부분 실패:** 다관점 fan-out에서 **일부 관점만** codex 호출이 실패하면 **실패한 관점만** 내부 서브에이전트로 채운다.
이미 성공한 관점을 다시 돌리지 않는다. 어느 관점이 폴백됐는지 사용자 보고에 적는다.
이것은 택일 규칙의 위반이 아니라 장애 대응이다.

**다음 사이클과의 관계:** 이 금지는 **한 라운드 안**에만 적용된다. 개선 후 2사이클째에 다시 리뷰하는 것은 정상이다.

**예외:** 관점 분할 fan-out과 적대적 검증은 이중 리뷰가 아니다. fan-out에서도 codex 우선은 유지된다 — 관점별로 (B) 경로를 호출한다.
**판별 기준과 경계는 `30-workflow.md`가 규범 원본이다.**

### 리뷰 지시문에 넣을 것

- **구현자 보고서는 증거가 아니라 주장이다.** 파일과 테스트에 대고 확인하게 한다.
- 새 테스트가 실제로 결함을 막는지 본다 — 구현을 일부러 망가뜨려도 초록이면 그 테스트는 아무것도 지키지 않는다.
- 화면 변경이면 유닛 테스트 통과를 화면이 맞다는 근거로 받지 않는다.

### 실행 명령

이 저장소는 보통 `main`에서 바로 작업하므로 **(B)가 기본**이다. (A)는 작업 브랜치가 따로 있을 때만 쓴다.

```bash
# (A) 작업 브랜치의 diff 전체 리뷰
# codex review는 -m을 받지 않고 --base와 지시문 인자를 함께 받지 않는다(codex-cli 0.162). 모델·샌드박스·지시는 -c로 넘긴다.
timeout 600 codex review --base main \
  -c model="gpt-6-astra" -c 'model_reasoning_effort="high"' -c sandbox_mode='"read-only"' \
  -c 'developer_instructions="IMPORTANT: node_modules/, graft/, graphify-out/, dist/, .worktrees/, .claude/ 아래와 미디어 볼륨은 읽지 말 것. 저장소 코드에만 집중하라."' < /dev/null

# (B) 기본 — 관점을 특정하거나 비교할 브랜치가 없을 때
timeout 600 codex exec -s read-only --skip-git-repo-check "<리뷰 지시문 + 대상 파일 경로/변경 내용>" \
  -m gpt-6-astra -c 'model_reasoning_effort="high"' < /dev/null
```

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 모델 | **최상위(flagship) 티어** = 현재 `gpt-6-astra` | `sol`·`terra`·`luna` 계열은 리뷰에 쓰지 않는다. 라인업이 바뀌면 `~/.codex/models_cache.json`의 설명에서 flagship 티어를 재확인해 갱신 |
| 노력 수준 | **`model_reasoning_effort="high"`** | 사용자 기본 설정이 `medium`이므로 **호출 시 반드시 명시 상향** |
| 샌드박스 | `read-only` | 리뷰는 읽기만 한다. 수정은 3단계에서 우리가 한다 |
| 타임아웃 | `timeout 600` + Bash 도구 `timeout` 파라미터 상향 | Bash 기본 120초로는 중간에 끊긴다 |

**폴백 시 보고:** 내부 폴백으로 리뷰했다면 그 사실과 사유(미설치 / 인증 실패 / 반복 타임아웃)를 사용자 보고에 명시한다(`40-reporting.md`).

## 3. 개선

**리뷰 지적도 주장이다.** 무비판적으로 반영하지 않고 각 지적을 먼저 분류한다.

1. **수용** — 근거가 확인됨 → 수정
2. **반박** — 코드/맥락 확인 결과 오지적 → 근거를 들어 반박을 기록하고 수정하지 않음
3. **보류** — 유효하나 이번 범위 밖 → HANDOFF의 남은 과제로 기록

수정은 `opus`가 한다. 지적이 **설계 수준**이거나 판정이 필요하면 분석/설계 등급(오케스트레이터 모델)으로 올려 다시 판단한다.

## 4. 루프 종료 조건

- **1사이클 = 구현 → 리뷰 라운드(1회) → 개선.** 사이클을 두 번 도는 것은 허용, 한 사이클 안에서 리뷰 라운드를 두 번 도는 것은 금지.
- 차단(blocking) 등급 지적이 0건이 되면 종료.
- **최대 2사이클.** 2회 후에도 남으면 더 돌리지 말고, 남은 지적과 판단 근거를 정리해 사용자에게 에스컬레이션한다.
- 수정 후에는 반드시 1단계 표의 게이트로 재검증한다. 재검증 없이 사이클을 닫지 않는다.
