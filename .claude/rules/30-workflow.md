# 30 — ultracode / 워크플로우 오케스트레이션

T3 작업이나 광범위 감사처럼 규모가 크거나 정확성이 중요한 국면에서는 `Workflow` 기반 멀티에이전트(ultracode) 적용을 허용한다.
**사용자가 이 지침으로 상시 승인한 범위이므로, 아래에 해당하면 별도 확인 없이 적용해도 된다.**

## 적용이 적절한 경우

- 다수 파일·다수 모듈에 걸친 마이그레이션 / 일괄 변경 (예: 인덱스 스키마 개정, 와이어 계약 변경의 백엔드·SPA·골든 동시 반영)
- 광범위 감사(audit), 전수 리뷰, 누락 탐색처럼 "빠짐없이"가 중요한 작업
- 독립적인 설계안을 여러 개 만들어 비교·심사해야 하는 경우
- 발견한 이슈를 **적대적 검증(adversarial verify)** 으로 걸러내야 하는 경우

## 적용하지 않는 경우

- T0~T2 작업, 단일 파일 수정, 대화성 응답, 기계적 소규모 작업
- 사용자가 빠른 확인만 원하는 경우

## 운영 방식

- `10-model-routing.md`의 모델 차등 규칙과 `20-review-cycle.md`의 구현→리뷰→개선 사이클을 각 단계(`opts.model`)에 그대로 적용한다.
- 탐색 단계는 인라인으로 먼저 훑어 대상 목록을 확보한 뒤, 그 목록에 대해 fan-out 하는 하이브리드 방식을 기본으로 한다.
- 병렬 에이전트의 파일·포트·스크래치 분리와 비상 정지는 `00-orchestration.md`를 따른다.

## 다관점 검증과 "이중 리뷰 금지"의 관계

> 이 절이 **예외 판별의 규범 원본**이다. 택일 규칙 자체의 원본은 `20-review-cycle.md`의 "2. 리뷰"다.

이중 리뷰 금지는 "**한 사이클의 리뷰 라운드 하나** 안에서 실행자를 codex와 내부 모델 중 하나로 정한다"는 뜻이다
(호출 실패로 인한 관점별 폴백은 예외 — `20-review-cycle.md`의 "부분 실패"). 사이클 단위 규칙이므로 개선 후 2사이클째 리뷰는 정상이다.
아래도 금지 대상이 **아니다.**

- **적대적 검증(adversarial verify)** — 이미 나온 지적 하나를 여러 검증자가 반박해 걸러내는 절차.
  리뷰를 한 번 더 하는 것이 아니라 리뷰 결과의 **참/거짓을 판정**하는 후속 단계다.
  **경계(이걸 넘으면 이름만 바꾼 2차 리뷰다):** 입력은 **이미 나온 지적 목록으로 한정**한다.
  변경분 전체를 다시 훑지 않고, 새 지적을 찾는 것도 검증자의 일이 아니다. 검증 중 새 지적이
  눈에 띄면 이번 라운드 산출물에 섞지 말고 **다음 사이클 입력으로 따로 기록**한다.
- **관점 분할 fan-out** — 정합성 / 계약 준수 / 동시성·자원 / 화면처럼 **서로 다른 관점**을 각 에이전트에 하나씩 할당해
  한 번의 리뷰 라운드를 구성하는 것. 같은 관점을 모델만 바꿔 반복하면 그것은 이중 리뷰다.

구분 기준: **같은 라운드 안에서 같은 대상을 같은 관점으로 두 번 훑으면 금지, 역할이 다르면 허용.**
codex 리뷰를 마친 뒤 같은 라운드에서 "혹시 모르니 내부 모델로 한 번 더"는 언제나 금지다.

**다관점 fan-out에서도 codex 우선은 유지된다.** 관점마다 `20-review-cycle.md`의 (B) 경로(`codex exec` + 관점 특정 지시문)를 호출한다.
내부 서브에이전트 fan-out은 codex를 쓸 수 없을 때의 폴백이다.
적대적 검증(참/거짓 판정)은 리뷰가 아니므로 `10-model-routing.md`의 분석/설계 등급 = 오케스트레이터 모델로 돌린다.
