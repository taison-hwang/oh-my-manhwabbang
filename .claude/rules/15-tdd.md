# 15 — 상세 구현은 TDD로 한다

- 대상: 판단이 들어간 코드 — `internal/` 패키지(스캐너, 아카이브 리더, 인덱스, HTTP 핸들러), `scripts/`의 게이트·도구,
  SPA(`web/src`)의 상태 처리. 설정, 골격, 문서, 기계적 변경은 대상이 아니다.
- 순서: 실패하는 테스트를 하나 쓴다 → 실행해 실패를 확인한다 → 그 테스트를 통과시키는 최소 구현을 쓴다 → 전체 테스트를 통과시킨다 → 정리한다. 테스트 하나 단위로 반복한다.
- 기대값은 명세에서 가져온다: `prd.md`의 FR/AC, `arch-backend.md` §7 계약, `decisions.md` 판정, `data-survey.md` 실측.
  구현을 돌려 나온 값을 기대값으로 옮겨 적지 않는다. 골든 파일(`internal/httpapi/testdata/golden/`)을 새 출력으로 덮어쓰는 것은 계약 변경이다(T3).
- 버그 수정은 그 버그를 재현하는 실패 테스트부터 쓴다. 픽스처는 **실제가 실패하는 방식으로 실패할 수 있어야** 한다 —
  캐시를 미리 채우거나 중간 상태를 만들지 못하는 픽스처는 아무것도 증명하지 않는다.
- 뮤테이션 자가검증은 T2부터: 스크래치 사본에서 구현을 일부러 망가뜨려 새 테스트가 실제로 빨개지는지 확인한다.
- 테스트를 약화하거나 허용오차를 넓혀 통과시키지 않는다. 못 고치면 못 고쳤다고 보고한다.
- 화면 변경은 유닛 테스트로 끝내지 않는다. 실제 브라우저에서 렌더링해 확인한다(CSS 캐스케이드처럼 유닛 티어가 보지 못하는 것이 있다).
- 구현을 위임할 때 서브에이전트 프롬프트에 TDD를 명시한다. 완료 보고에는 먼저 쓴 테스트와 실패 확인 결과를 넣게 한다(`20-review-cycle.md`의 자체 검증 결과에 더한다).
