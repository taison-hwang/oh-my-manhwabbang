사용자가 §5.6.1 **J**를 재검토해 **하기로 결정했고**, D-33 / E-3을 뒤집는 판정 **E-26** / 개정 **A-11**로

| 결정 | |
|---|---|
| 반영 시점 | **재시작 기반.** 루트는 기동 시 한 번만 열리고(`app.go` `source.OpenRoots`) 리로드 경로가 없다. 핫-애드는 사용자가 물리쳤다 |
| 보안 | 새 키 **`server.allow_root_editing`**(기본 **false**). 꺼져 있으면 **`403 forbidden`** — `ErrorCode`에 새로 추가한 코드다. `unauthorized`를 재사용하면 `isAuthError`가 **로그인으로 풀 수 없는 거부를 로그인 화면으로** 보낸다(E-17) |
| 제거 (**R1**) | YAML에서 빼고 **그 루트의 `index.db` 행까지 지운다.** 그래야 "제거"가 사용자가 아는 제거가 된다. **`user.db`의 진행률은 건드리지 않아** 같은 폴더를 다시 추가하면 다시 붙는다 |
| 추가 (**R2**) | 파일에는 있으나 아직 열리지 않은 **대기(pending) 행**으로 보인다. 재스캔은 제공하지 않고, 재시작이 그것을 실재로 만든다 |
| 경로 | 직접 입력 + 서버 검증. **파일시스템 브라우저는 없다**(디렉터리 목록 API는 새 노출면이다) |
| 파일 쓰기 | 같은 디렉터리 임시파일 → fsync → rename, 모드 보존, `.bak`. **주석 보존 왕복이 바이트 단위로 일치한다** |

> **`yaml.v3` Node 왕복은 이 파일을 망가뜨린다 — 실측: 15,281 B/277행 → 14,217/252.** 주석 블록의 빈 줄이
> 사라지고 2→4칸으로 재들여쓰기된다. 그래서 Node는 **행 범위 탐색에만** 쓰고 실제 편집은 텍스트
> 스플라이스다. 다시 "그냥 Marshal하면 되지 않나"가 나오면 이 숫자를 보라.

**검증 규모**: 구현자 2 → 1차 리뷰(뮤테이션 68건 중 62건 빨강) → 수정 2 → 2차 리뷰(수정본 뮤테이션) →
수정 1 + e2e 커버리지 1. **리뷰 지적 3건이 반증됐고, 그중 2건은 적용했으면 결함을 고정하거나 새로
만들었을 것이다** — 쓰기 순서 단언(§7.4 원문이 반대를 말한다), 제거집합 두 번째 가드(가드 자체가
틀렸다), 그리고 프런트 게이트-오프 테스트(구현 전부터 통과하고 있었다).

> **가드가 틀렸던 건이 특히 값졌다.** 제거집합은 이름으로 키를 잡는데 이름 생성기는 은퇴한 이름을
> **일부러** 돌려준다(그래야 진행률이 다시 붙는다). 그래서 "라이브러리를 새 디스크로 옮기기" —

> 숨기고, 다시 추가하려 하면 `duplicate`로 거절**했다. 리뷰어는 "이 가드를 검사하는 테스트가 없다"고만
> 봤고, 수정자가 가드 자체를 의심해서 잡았다.

**e2e 커버리지가 이번에 생겼다 (§4.6).** 합성 라운드가 `allow_root_editing: true`로 쓰기 경로를 실제로

### 4.4 그 수정이 넣은 검사 하나가 §6.5 그 자체였다 — 리뷰가 잡았다

같은 라운드에 `scripts/e2e.sh`의 AC-005에 "재구축된 라이브러리가 지워진 그것과 이름까지 같은가"를
새로 넣었다. 그런데 **이름을 하나도 읽지 않고 PASS를 찍고 있었다.** `?limit=500`인데 이 엔드포인트의
상한은 **200**이고(`internal/httpapi/series.go:19`, `arch §7.5`는 `limit | int 1..200`), `set -e`가
꺼져 있어 400이 나도 중단되지 않는다. 양쪽 변수가 `""`로 남고 `[ "" = "" ]`가 참이 된다.
**§6.5를 없애려고 넣은 코드가 §6.5가 됐다.**

세 겹으로 고쳤다 — 요청받은 것보다 한 겹 더:
1. 문서화된 상한 `limit=200`,
2. 빈 문자열 비교로 통과하는 경로 제거 — 선행조건을 **결과에 접지 않고 따로** 단언,
3. *스스로 추가* — 응답이 잘리면(`items != total`) 크게 실패. 나중에 서브셋이 200을 넘으면
   **똑같이 잘린 두 접두사가 서로 같다고** 통과할 수 있었다.

그리고 **초록을 보는 것으로 끝내지 않고 빨갛게 만들어 증명했다.** 검증자는 구현자의 방법(로그
감시 레이스)을 쓰지 않고 자기 방식으로 다시 했다 — 인덱스 삭제와 재스캔 **사이**에 env 가드를 건
결정적 주입을 넣어 rc=1과 이름 단위 diff를 얻었다. PASS 줄의 `(N names read back)`은 목록에서
유도한 수라, **목록을 읽지 않고는 인쇄될 수 없다.**

같은 라운드에 스크린샷 게이트도 고쳤다: 하드코딩 97 대신 스펙에서 `shot()` 호출 25개를 추출해

### 5.2 [해결됨 — 제품 결함 아니었음] E2E 10단계 "got 200" — 판정 E-22

```
FAIL  expected 404 for a book with no index row, got 200
```

**이전 판의 이 항목은 틀렸다.** `internal/httpapi/books.go`를 의심하고 계약이 모호할 수 있다고 적어
두었으나, 계약은 모호하지 않고 코드도 옳다. **200을 응답한 것은 우리 서버가 아니었다.**

무슨 일이 있었나 — 이전 디버깅 세션이 남긴 `shelf` 프로세스가 `:8791`을 이미 점유하고 있었다
(`data_dir: /tmp/shelf-e2e-dev/data`). E2E가 띄운 바이너리는 포트를 잡지 못하고 즉시 종료했는데,
`start_server()`가 `kill -0 "$server_pid"`보다 `curl /api/health`를 **먼저** 검사했기 때문에 남의 서버가
준 200을 자기 서버의 기동 성공으로 오인했다. 그래서 10단계가 지운 인덱스는
`/tmp/shelf-e2e-3286544/data/index.db*` — **아무도 쓰지 않던 파일**이었고, 질의는 인덱스가 멀쩡한 남의
서버로 갔다. 결정적 증거: 이 실행의 `run_id f6a067bd84cab711`(`docs/e2e-last-run.log:23`)이
`/tmp/shelf-e2e-dev/server.log:1182`에 찍혀 있고, 같은 로그에 10단계 요청열 전체와
`GET /api/books/i4kixpa2b2oxpcg5 status=200`(00:41:41.536)이 그대로 남아 있으며, 그 로그에는
00:19:51~00:49:52 사이에 **재기동 흔적이 없다.**

계약 판정 (전문은 `docs/decisions.md` **E-22**):
- `arch-backend.md:1391` §7.1 — 형식은 맞으나 알 수 없는 id는 **404**.
- `arch-backend.md:1758` §7.6 — *"`404` for an unknown `bid`. Books with `status != "ok"` still return 200 …"*
  한 문장 안의 **서로 다른 두 경우**다.
- impl-plan §4 #4의 `status != "ok"` → 200 규칙은 **행이 있는데 status가 나쁜 책**에만 적용된다.
  `status`는 `books` 테이블의 컬럼이므로(`internal/index/books.go:36-38`) **행이 없으면 status도 없다.**
- 코드는 이미 404를 낸다(`internal/httpapi/books.go:40-46`, 폴백 분기 없음). 단위 테스트
  `internal/httpapi/api_test.go:138-169`가 이미 이를 단언하고 통과한다.

**한 일** — `scripts/e2e.sh`에 가드 4개 추가(각각 실제로 발화하는 것을 확인한 뒤 반영):
① 스폰 전 포트 선점 검사 후 `die`, ② 폴 루프에서 health보다 **자식 생존 확인을 먼저**,
③ `/api/health`의 `uptime_ms`로 응답자 신원 확인, ④ `stop_server`가 **포트가 실제로 조용해졌는지** 증명.
제품 코드·`web/**`·golden 파일은 **한 줄도 건드리지 않았다.**

**리뷰가 가드를 뚫었고, 그것도 고쳤다.** 가드 ③은 *오래된* 유령만 잡는다 — 갓 시작된 유령
(`uptime_ms=40`)은 ①②③을 전부 통과했다(개발용 오토리로더 재시작이 남기는 ~200ms 창이 정확히 그 틈이다).
그래서 **`ss`로 포트 소유자 PID가 우리 자식과 일치하는지** 대조하는 가드를 추가했고, `/proc/<pid>/exe`가
`$BIN`인지도 본다. `ss`가 없으면 조용히 통과시키지 않고 크게 실패한다.

같은 리뷰에서 나온 심각한 것 2건도 함께 고쳤다.
- **`trap cleanup EXIT INT TERM`이 종료를 하지 않아** SIGTERM을 받은 실행이 상태 디렉터리가 지워진 채
  4단계를 더 진행하고 **exit 0으로 성공 보고**했다. 이제 INT/TERM은 cleanup 후 130/143으로 종료한다.
- **`cleanup()`이 Playwright 트리를 회수하지 못했다.** 원인은 bash가 트랩된 시그널을 현재 **포그라운드**
  명령이 끝날 때까지 미룬다는 것 — 기존 형태는 브라우저 실행 내내 SIGTERM을 무시했다. 백그라운드 +
  `wait` + 프로세스 그룹 kill로 바꿨다. (이전 세션이 남긴 9.5분짜리 고아 Playwright의 원인이 이것이다.)

**결과**: 최종 라운드에서 10단계가 `PASS  with index.db deleted the book is 404, as it must be`로 통과했다.

**이전 판의 이 항목은 일을 막고 있었고, 막을 이유가 없었다.** 거기엔 "덮으려면 세로 페이지를 가진

적혀 있었다. **커레이티드 10개 안에 이미 100% 세로인 볼륨이 둘 있다.** 읽기 전용 컬렉션을 PIL과
poppler로 **전수** 실측했다 (표본이 아니라 100%):

| 시리즈 | 1권 | 세로 비율 (실제 모드) | 합성 모드 (D-49) |
|---|---|---|---|
| `[만화] 자살도114-122` | 낱장 181장 | **181 / 181 = 100%** (modal 800×1132 등) | 11 / 11 세로 |
| `[만화] 미생 1~9 (완결 pdf)` | 미생 1권.pdf | **306 / 306 = 100%** (MediaBox ~378×548pt) | 4쪽 × 595×842 세로 |

군계의 104/104 가로 주장은 독립적으로 재확인됐다 — 그 부분은 옳았다. 하지만 **결론이 틀렸다.** 명세
범위 변경은 필요하지 않았다. (판정 **E-23**을 참조 — 이제 이것은 구속력 있는 결론이다.)

**이전 판의 넓은 문장도 너무 셌다.** "두 프레임의 실제 DOM 순서는 E2E가 한 번도 본 적이 없다"는 문장
중 **"두 프레임을 본 적이 없다"는 거짓**이다. `05-pdf-and-large.spec.ts`의 6.8이 미생 PDF에서 양면 RTL
스프레드를 **이미 렌더링하고 단언하고 있었고**, 네 뷰포트 전부에 대한 증거가
`docs/e2e-shots/step-06-8b-viewer-pdf-rtl-spread-{desktop-1440,laptop-1024,tablet-768,mobile-400}.png`로
남아 있다(2026-07-29 04:47~04:49 클린 라운드). tablet-768 샷은 016이 오른쪽, 017이 왼쪽인 것을 육안으로
보여준다.

**실제로 비어 있던 것은 더 좁고, 더 다른 것이었다 — 네 가지.**

1. **`04-viewer.spec.ts`의 `if (paired)`는 두 모드 모두에서 구조적으로 죽어 있었다.** 실제 모드에서는
   군계가 전부 가로여서. 합성 모드에서는 **군계의 합성 쌍둥이가 4쪽**이라 `TURNS = 5`번을 누르면
   `landed === total`이 되고 `landed + 1 <= total`이 거짓이 되어서. 이전 판은 앞의 이유만 적고 있었다.
2. **DOM 순서만은 어느 E2E도 단언한 적이 없다.** 두 블록 다 프레임을 *페이지 번호로* 찾아 x를
   비교했다(`xs.find(f => f.n === landed)`). 그런데 `docs/impl-plan.md:638`(WP-11 수용기준 4)은 "DOM-order
   test"를 **이름으로** 요구한다. 그것을 강제하는 검사는 `ViewerPage.test.tsx:342`(jsdom) 하나뿐이었고,
   **591개 유닛 테스트 중 프레임을 뒤집었을 때 빨개지는 유일한 테스트**임이 뮤테이션으로 증명됐다.
3. **두 블록 다 조용히 건너뛸 수 있는 가드 뒤에 있었다** — `if (paired)`와 `if (count === 2)`.
   §6.5의 모양 그대로다. FR-VWR-004가 망가져 짝이 안 지어지면, 규칙이 빨개지는 대신 **검사 자체가
   사라진다.**
4. **실측으로 새로 드러난 것 — desktop-1440에서 6.8의 스프레드 단언이 *칠해지지 않은* 프레임에 대고
   통과하고 있었다.** 디코드되지 않은 `PageFrame`은 자식 `<img>`가 `position:absolute; opacity:0`이라
   **콘텐츠 폭이 0**이 된다. 폭 0의 보이지 않는 박스지만 bounding rect는 여전히 있다. 그래서
   `count === 2`도 통과하고 `x(n) > x(n+1)`도 통과한다. 보존된 스크린샷을 픽셀 단위로 스캔해 증명했다:
   흰 런이 정확히 하나, CSS x `[423.0, 1019.0]`, 폭 596, 중심 **721.0**. 두 프레임 모델(596px + 0px +
   2px gap, `row-reverse`)이 예측하는 값과 일치하고, 한 프레임 모델(중심 720.0)은 배제된다. 그 한 장에
   찍힌 폴리오는 016 = `start`이므로 칠해지지 않은 쪽은 `start + 1`이었다. 나머지 세 뷰포트는 같은
   방법으로 스캔했을 때 두 개의 실제 런이 나온다(laptop-1024 `[6,512]`/`[514,1018]`, mobile-400
   `[0,200]`/`[202,400]`).

**한 일**

- `05-pdf-and-large.spec.ts` 6.8 — `if ((await frames.count()) === 2)` 가드를 무조건 단언
  `toHaveCount(2)`로 바꾸고, `[data-role="page-frame"][data-status="ready"]`가 2개가 될 때까지 기다리는
  전제조건(30초)을 추가했다. **이 전제조건이 4번을 막는 유일한 검사다.** `before`/`after` 양쪽에 DOM
  순서 단언을 넣었고, 기존 x-기하 단언은 하나도 건드리지 않았다.
- `04-viewer.spec.ts` — 죽은 `if (paired)` 블록을 지우고, *왜* 군계가 두 모드 모두에서 짝지을 수 없는지
  주석으로 남겼다. 그 자리에 **`6.6b`**를 새로 추가했다: 자살도를 UI로 열어 `page_count`에서 시작 쪽을
  유도하고(하드코딩된 쪽 번호 없음 — `shelf.ts` 규칙 1), 두 쪽이 세로임을 API에서 확인한 뒤, **무조건**
  프레임 2개 · 둘 다 `ready` · L→R과 R→L 양쪽에서 DOM 오름차순 · x 순서를 단언한다. 6.6의
  `if (!paired)` 가드도 무조건 `expect.poll` 단언으로 바꿨다. 6.6은 군계에 그대로 남았다 — 커레이티드
  10개 중 **FR-VWR-004의 가로 자동 분할을 실행하는 유일한 볼륨**이기 때문이다.
- **그리고 6.6이 이제 `expect(paired).toBe(false)`를 단언한다.** 이게 없으면 "군계는 짝짓지 않는다"는
  것이 *검사되지 않는 산문*으로 남는다 — `toHaveCount(paired ? 2 : 1)`은 치수가 무엇을 함의하든 그것에
  동의할 뿐이라 두 분기가 다 만족 가능하고, 컬렉션이나 픽스처가 바뀌면 위 주석과 6.6b를 가리키는
  포인터가 아무것도 실패시키지 않은 채 허구가 된다.
- `6.6b`는 자살도에 만든 진행률 행을 **나갈 때 지운다**(`DELETE /api/books/{bid}/progress`, FR-VWR-012의
  안읽음 엔드포인트). 지우지 않으면 `SeriesCard`/`SeriesRow`가 그 행에서 진행률 바를 그리므로,
  **desktop-1440(01-library가 04-viewer보다 먼저 도는 첫 프로젝트)의 라이브러리 샷에는 바가 없고 나머지
  세 프로젝트에는 있는** 상태가 되어 §7.4 리뷰 세트 ~10장이 제품과 무관한 이유로 서로 달라진다.
  `shelf.ts` 규칙 2("모든 테스트는 서버를 발견한 상태 그대로 두고 나간다")가 이것이다.

**정직하게 기록해 둘 것 — DOM 순서 단언 자체는 새 뮤테이션 커버리지를 사지 않는다.** 리뷰어가 출하된
`fit.ts`를 그대로 import하는 레이아웃 하네스로 확인했다(먼저 보존된 스크린샷의 실측 픽셀에 캘리브레이션
한 뒤 뮤테이션을 걸었다). 프레임이 정확히 2개이고 순서를 정하는 것이 flex-direction뿐일 때, **기존
`data-flow` 단언 + x 비교 쌍이 이미 DOM 순서를 결정한다**: 배열을 뒤집으면 x 검사가 빨개지고, 배열을
뒤집으면서 flow를 `row`로 되돌리면(`fit.ts`가 경고하는 이중 부정) `data-flow` 검사가 빨개진다.
정찰 보고 두 건의 "내림차순 DOM도 통과한다"는 주장은 **틀렸고**, 구현자가 그것을 정정했다. DOM 순서
단언이 자리를 얻는 이유는 `impl-plan.md:638`이 이름으로 요구하기 때문이고, flex-direction 말고 다른
것(`order:`, `direction:`)이 스테이지를 정렬하는 순간 그 추론이 죽기 때문이다. **이번 변경이 실제로 새로
잡는 것은 두 가지다**: 가드→단언 전환(3번)과 `ready` 전제조건(4번). 둘 다 뮤테이션으로 빨개지는 것을
확인했다.

> 항목 1을 **이름으로** 가리킨다. 이 문서는 세션마다 재작성되므로 이 문단을 옮기더라도 인용은
> 살아남지만, **제목을 바꾸면 죽는다.** 다시 행 번호로 되돌리지 말 것.
> (이번 세션의 §5.6 항목 1·2가 통째로 행 번호가 어긋나 있던 것과 정확히 같은 실패였다.)

정확한 술어는 이미 프로세스 안에 `thumbs.Service.idle()`로 존재했지만, `Stats()`가 필요한 두 필드를
내보내지 않았다. **그래서 `active`(작업 중인 워커 수)와 `inflight`(singleflight 안의 서로 다른 키 수)를
`thumbs.Stats` → `httpapi.ThumbCounter` → `GET /api/health?verbose=1`로 내보내고**, sleep을 네 카운터
(`cover_depth`/`page_depth`/`active`/`inflight`)가 전부 0이 될 때까지의 **한도 있는 폴링**으로 바꿨다.
한도(30초)를 넘기면 조용히 넘어가지 않고 `r.check(False)`로 **FAIL한다**. 헬퍼의 독스트링이 왜 이 네
개의 논리곱이 추측이 아닌지를 적고 있다 — 한 작업은 enqueue부터 워커가 집을 때까지 `cover_depth`/
`page_depth`가, 워커의 차례 내내 `active`가, 캐시가 write-temp-then-rename을 마칠 때까지 `inflight`가
붙들고 있으므로, **넷이 다 0이면 서비스가 받은 모든 썸네일이 최종 경로에 있다.**

> 이전 판이 대안으로 제시한 `thumbs.{queued,generated,failed}`를 쓰지 않은 이유는 **코드에는 적혀 있지
> 않다**(직접 확인함 — 독스트링은 네 카운터가 왜 건전한지만 설명한다). 이유는 이렇다: `queued`는 커버와
> 페이지 썸네일을 **같은 `enqueue()`**로 세므로 커버 전용 진술이 아니다. 이 curl 스크립트는 페이지
> 썸네일을 요청하지 않지만 브라우저는 하고, 헬퍼가 재사용되는 순간 그 가정이 깨진다.

> **부작용, 그리고 아직 아무도 판정하지 않은 것.** 이것으로 저 네 필드가 **게이트가 의존하는 사실상의
> 계약**이 됐다. 그런데 `arch-backend.md` §7.4는 `?verbose=1` 페이로드를 아예 명세하지 않고
> ("Add `?verbose=1` for pool counters"가 전부), `internal/httpapi/dto.go`는 그 블록을
> *"diagnostics, not contract"*라고 적고 있다. 구현자는 이 모순을 `dto.go` 주석에 정직하게 남겼고 문서는
> 건드리지 않았다. **누구도 이것을 판정한 적이 없다 → 아래 열린 항목 D.**

#### 항목 2 — AC-008 지연 측정. 닫힘, 그리고 인수인계가 모르던 판정이 나왔다.

세 가지가 실제로 틀려 있었다. (a) `target`(= 900)을 **워밍한 뒤 그 페이지를 잰다** — 5개 표본 중 하나가
오염돼 있었다. (b) 주석이 *"NFR-PRF-001 is about a cached page"*라고 적고 있었는데, **ZIP 페이지에는
서버측 페이지 캐시가 아예 없다** (`serveArchivePage`는 저장된 오프셋에서 바로 스트리밍한다). "warm"이
가리킬 수 있는 것은 openpool 핸들과 인덱스 행뿐이고, 그것이 I-8이 말하는 warm이다. (c) 페이지별 검사가
**실패할 때만** `r.check`를 불러서, 리포트가 찍는 단언 개수가 결과에 따라 달라지고 통과한 실행은 아무
증거도 남기지 않았다.

**그리고 인수인계에 없던 것**: `docs/impl-plan.md:966`(§6.3 5단계)이 **이 스크립트를 이름으로 서술하며**
`GET /api/books/{battle_royale}/pages/900`을 `200 image/jpeg`로 **200 ms 미만**이라고 **못박고 있다**
(`scripts/e2e.sh`의 단계 이름 자체가 `7 · curl assertions (impl-plan §6.3 step 5)`이다). 즉 **200 ms는
습관이 아니라 판정이고, 페이지 900은 측정 집합에 남아 있어야 한다.** 첫 수정본은 점프 집합을
`page_count`의 5분위로 유도하면서 900을 떨어뜨렸다 — 명세가 이름으로 든 요구사항이 조용히 사라진
것이었고, 리뷰가 그것을 잡았다. 최종 형태는 900을 무조건 포함하고, "이 볼륨은 900쪽에 도달한다"를
**단언되는 선행조건**으로 만든다(`{900} if pc >= 900 else set()` 같은 가드는 §6.5의 모양이라 쓰지
않았다). I-8의 100 ms와 충돌하지 않는다 — I-8은 50회 warm 점프의 p95 **TTFB**이고 이쪽은 소수의
**cold** 점프 중 최악의 **마지막 바이트**까지다. 두 개의 서로 다른 측정이다. 판정 **E-24**로 기록했다.

워밍업(페이지 1, 3회)도 이제 결과를 단언한다. 낡은 `?v=`는 409를 주는데, 그러면 풀이 차가운 채로
남아 1.34 GB 컨테이너 여는 값이 첫 점프에 청구되고 **AC-008과 무관한 이유로 AC-008이 빨개진다.**

#### 항목 3 — `clearSearch()`. 확인됨, 삭제.

죽은 코드였다(정의 1개, 호출자 0개). 그리고 인수인계가 적은 것보다 결함이 하나 더 있었다: 필드가 이미
비어 있으면 **아무것도 단언하지 않고 조용히 반환**한다 — 열두 줄 위의 `setView()`가 그 안티패턴을
피하려고 쓰여 있고 그 이유가 문서화돼 있는데도. 세 번째는 `shelf.ts` 자기 파일 규칙 1("하드코딩된 쪽
수·권 수 금지") 위반이다. 검색 지우기 동작은 `library.test.tsx`가 **개수가 아니라 이름으로** 이미
커버하고 있으므로 삭제로 잃은 커버리지는 없다.

**여기서 딸려 나온 것**: `shelf.ts`의 `SERIES` 주석이 이 열 개 리터럴을 *"the one set of literals both
modes share"*라고 적고 있었는데 **거짓**이다. 같은 열 개 문자열이 **서로 독립적인 사본 네 벌**로
존재한다 — `scripts/e2e-config.sh`, `scripts/e2e-assert.py`, `web/e2e/shelf.ts`,
`scripts/mkfixture/main.go`. 주석은 사실대로 고쳤지만(네 집을 이름으로 적고, 정적으로 연결된 것은 없으며
실행이 실패해야만 불일치가 드러난다고), **사본 자체는 그대로다 → 아래 열린 항목 A.**

#### 항목 4 — **오진이었다.** 그리고 옆에 진짜 구멍이 있었다.

"어느 tier도 `상세` 버튼을 클릭하지 않는다. `onResume`으로 바꿔도 전 테스트가 통과한다"는 **거짓**이다.
`web/src/features/library/library.test.tsx:549`가 그 버튼을 클릭하고 목적지를 단언한다. **두 에이전트가
독립적으로 뮤테이션했고 둘 다 빨개졌다**: `onClick={onOpen}` → `onClick={onResume}` 한 줄 변경 →
`Tests 1 failed | 38 passed (39)`, `library.test.tsx:550`에서 `Unable to find an element with the text:
series detail`, DOM에는 `<p>viewer</p>`. 그 테스트의 주석은 애초에 **이 뮤테이션을 위해** 쓰였다고
스스로 적고 있다.

**왜 살아남았나**: 이 문서의 mtime(`04:53`)이 `library.test.tsx`의 mtime(`01:54`)보다 **나중**이다. 즉
그 사이에 테스트가 생겼는데, 문장은 다시 확인되지 않은 채 이월됐다. §6.5의 패턴이 한 tier 위에서 그대로
재현된 것이다 — **검사가 아니라 문서가, 출하되는 대상이 아니라 예전의 그것을 보고 있었다.**

**옆에 있던 진짜 구멍**: 어느 tier도 오버레이 버튼이 **도달 가능한지**를 증명하지 않았다. 두 버튼 모두
`pointer-events-none`이고 `group-hover`/`group-focus-within` 게이트가 뒤집어야 살아난다. 그 게이트를
지워도 **유닛 39개가 전부 그린이다** — `web/vitest.config.ts`가 `css: false`라서 Tailwind가 로드되지
않고, `getComputedStyle`이 `pointer-events: auto`를 보고하며, `user-event` 자신의 포인터 가드가
공전(空轉)한다. §6.5 4행과 §5.3 1번이 같은 얘기다.

그래서 유닛 테스트를 추가하는 대신 **Playwright 테스트 하나**를 추가했다 —
`01-library.spec.ts`의 **`6.1 (overlay buttons)`**로, 바로 위 `6.1 (overlay)`의 호버 전제를 그대로
재사용한다. (두 테스트 다 impl-plan §6.3의 번호를 쓰지 않는다. 원래 `6.4`로 붙어 있었으나 그 번호는
`02-palette.spec.ts`의 Ctrl+K 팔레트 단언 것이라, 이 세션에 오버레이 회귀 가드 **한 쌍**으로 개명했다.)
두 버튼 다 `pointer-events: auto`임을 단언하고, 기본 버튼은
`click({trial: true})`로 **히트테스트만** 거치고(뷰어를 열어 진행률을 쓰지 않기 위해), `상세`는 실제로
클릭해 시리즈 화면에 착지하고 뷰어가 안 열리는 것을 단언한다. 실제 Chrome CDP 하네스로 다섯 개
뮤테이션을 돌려 검증했다 — 출하 클래스에서는 두 버튼 모두 `elementFromPoint`가 자기 자신을 돌려주고,
`상세`의 게이트만 지우면 `상세`만 빨개지며, 기본 버튼의 게이트만 지우면 기본 버튼만 빨개진다
(768/400 티어의 카드 폭 326px·172px 양쪽에서 동일). **그래서 두 버튼을 다 단언하는 것이 중요하다.**

> **여기서 제품 결함이 하나 승격됐다.** `SeriesCard`의 오버레이에는 `[@media(hover:none)]` 폴백이
> 없다. 같은 프로젝트의 `VolumeTile`은 그 폴백을 이미 출하하고 있다. 즉 **진짜 터치 기기에서는
> 오버레이가 영원히 `opacity:0` + `pointer-events:none`이고 두 버튼에 도달할 방법이 없을 수 있다.**
> 새 Playwright 테스트도 이것을 보지 못한다 — `hover()`는 진짜 마우스 이벤트를 보내므로 마우스에
> 대한 도달 가능성만 증명한다. 이 세션에서 발견돼 별도 수정 에이전트에게 넘겼다. **최종 상태는
> 아래 열린 항목 C에서 확인할 것** — 이 문서를 쓴 시점에는 아직 반영되지 않은 상태였다.

개명하면 네 파일 편집이고, 어긋나면 컴파일이 아니라 **실행이** 실패한다. `shelf.ts` 주석은 이제 이

**B. ~~`01-library.spec.ts` 리스트 모드의 살아 있는 `toHaveCount(CURATED_SERIES_COUNT)`~~ — 닫힘.**
항목 3에서 `clearSearch()`를 지운 바로 그 결함 모양이 6.2에 **죽지 않고 살아** 있었다. 통과하던 이유는

6.2는 이제 그리드 모드(6.1)와 같은 형태로 바뀌었다 — 기대값은 API(`seriesFacts`)에서 읽고, `walkLibrary`로
가상 스크롤러를 순회한 뒤 **이름 집합**을 비교한다. 저장소 전체에서 살아 있는
`toHaveCount(CURATED_SERIES_COUNT)`는 하나도 남지 않았다(남은 한 건은 그 자리에 무엇이 있었는지 적은
주석이다). **이 줄은 지우지 말고 남겨둘 것** — 같은 모양이 세 번째로 나타나면 이것이 전례다.

**C. `SeriesCard`의 호버 오버레이에 `[@media(hover:none)]` 폴백이 없다 — 판정 대기.**
(§5.6 항목 4에서 승격된 건.) **문서를 넘기는 시점에 직접 확인함**: 폴백은 **일부러 추가되지 않았고**,
그 근거가 컴포넌트 안에 길게 적혀 있으며, 마지막 줄이 *"Changing that is a product ruling, not a
component's call; escalated with no ruling in decisions.md yet"*이다. 근거 요약:

- 터치 기기가 잃는 것은 **목적지가 아니라 단축키**다. `상세`와 커버는 **같은 `onOpen`** prop이고,
  시작하지 않은 시리즈에서는 `onResume`도 `onOpen`으로 떨어진다(열 책 id가 없으므로). 남는 것은 "시작한
  시리즈를 한 번에 이어보기"뿐인데, 그 경로는 시리즈 화면의 항상 보이는 `이어 읽기` 버튼과 같고 그
  화면은 이 카드가 이미 응답하는 탭으로 간다.
- `VolumeTile`이 폴백을 갖는 이유는 그 화면에 두 번째 경로가 **없기** 때문이고, 그쪽 오버레이는
  66×29 px 코너 버튼인 반면 이쪽은 `inset-0` 전체를 덮는 `--scrim-cover`(ink 72%)다. 같은 클래스를
  그대로 옮기면 **모든 터치 기기에서 그리드의 모든 커버가 스크림으로 덮인다.**

즉 지금 상태는 "고쳐지지 않은 결함"이 아니라 **근거가 적힌 미판정 사항**이다. `ui-spec` §4.5는 오버레이를
"호버로 드러난다"고 명세하면서 터치 기기가 무엇을 받는지는 말하지 않으므로, **판정이 필요하다.**

**판정이 "폴백을 넣는다"로 나면 주의**: 스크림(`bg-scrim-cover` div)은 **무조건**
`pointer-events-none`으로 남아야 한다. 안 그러면 §5.3 1번(커버 클릭이 죽던 결함)이 터치 기기에서 그대로

`/api/roots`는 GET 전용(`router.go:254`), `internal/config`는 읽기 전용(제품 코드에 `yaml.Marshal`이
하나도 없다).

뒤집으려면 E-3이 이미 견적을 내 뒀다 — `POST/DELETE /api/roots`, 원자적 rename과 **주석 보존**이 되는
YAML writer, traversal 방어가 되는 경로 검증, 파일시스템 브라우저가 있는 온보딩. E-3의 표현으로
*"roughly a whole extra work package, and a new security surface"*. **먼저 I를 닫는 것이 훨씬 싸고,
사용자가 실제로 겪는 불편의 상당 부분을 해소할 가능성이 높다** — 지금은 편집하라는 파일이 어디 있는지도
모르는 상태이기 때문이다.

> **4세션차 갱신 ①**: I는 닫혔다. 이제 사용자는 편집할 파일의 절대경로를 설정 화면에서 본다.
> **갱신 ② — J도 닫혔다.** 다시 물었더니 사용자가 **하기로 결정**했고, 판정 **E-26**(+ 같은 날 REVISION)
> 과 개정 **A-11**을 먼저 쓴 뒤 구현했다. 전문은 §1.2와 §4.6. 절차 자체는 지켜졌다 — 판정이 코드보다
> 먼저 갔고, 사용자 결정이 없는 갈림길(반영 시점 · 보안 게이트 · 경로 입력 방식)은 물어서 정했다.
>
> 남아 있는 **미판정 사항 하나**: 유효한 UTF-8이 아닌 이름의 디렉터리는 이 엔드포인트로 **영영 추가할 수
> 없다.** `encoding/json`이 디코드에서 U+FFFD로 치환하므로 서버는 디스크에 없는 경로를 받고
> `does_not_exist`("그런 디렉터리가 없습니다")로 답한다 — 사용자가 눈으로 보고 있는 디렉터리에 대고.
> 계약은 안전하다(아무것도 쓰이지 않는다). 고치려면 `RootCreate.path`를 base64나 퍼센트 인코딩으로
> 바꿔야 하므로 **패치가 아니라 판정**이다. CP949 파일명이 흔한 컬렉션이라 남겨 둔다.

**저장소에 파일을 남기지 말 것 — 특히 `.pyc`.** 3세션차에 `python3 -m py_compile scripts/e2e-assert.py`가
`scripts/__pycache__/e2e-assert.cpython-312.pyc`를 남겼고, 리뷰가 잡아 지웠다. 이번엔 9단계 마커보다
오래된 파일이라 게이트에 걸리지 않았지만, 다음번엔 걸린다.

> **`PYTHONDONTWRITEBYTECODE=1`도 `python3 -B`도 이것을 막지 못한다** — 그 둘은 *import* 기계만
> 통제하고 명시적 컴파일은 통제하지 않는다. 직접 확인했다: `PYTHONDONTWRITEBYTECODE=1 python3 -B -m
> py_compile m.py`는 깨끗한 디렉터리에 `__pycache__`를 만든다. 유일하게 통하는 방법은 출력을
> 저장소 밖으로 돌리는 것이다 —
> `python3 -c "import py_compile; py_compile.compile(src, cfile='<스크래치>/out.pyc', doraise=True)"`.
> `.gitignore`는 **일부러** `__pycache__`를 무시하지 않는다. 무시하면 `git status`에서는 안 보이면서
> 9단계는 그대로 터지고, 그때 나오는 메시지는 미디어 볼륨 얘기라 원인을 못 찾는다. 이유가 `.gitignore`
> 안에 적혀 있다.

**저장소 안에서 앱을 띄우지 말 것.** 3세션차에 `dist/shelf --config shelf.yaml`이 저장소 루트에서

## 6.5 이 프로젝트에서 결함이 살아남는 방식 — 하나의 패턴

리뷰 4회와 E2E 전체 사이클을 뚫고 살아남은 결함은 거의 전부 같은 모양이었다.
**검사가 출하되는 대상이 아니라 그 옆의 것을 보고 있어서, 정확성과 무관한 이유로 통과한다.**
두 세션에 걸쳐 **독립적으로** 발견된 사례들 — 뒤의 다섯 줄이 3세션차에 추가됐다:

| 검사가 본 것 | 봤어야 할 것 |
|---|---|
| `CGO_ENABLED=0` 플래그 | 산출물의 ELF 헤더 (실제로는 동적 링크였음 — E-21) |
| 태그 없는 `go test` | 출하 태그셋 `-tags noavif` (골든 스위트가 실패하고 있었음) |
| `curl /api/health`의 응답 | 포트 소유자 PID가 우리 자식인지 (남의 서버가 채점 중 — E-22) |
| jsdom + `css:false` | 실제 브라우저 히트테스트 (커버 클릭이 죽어 있었음) |
| 60초 메모된 `/api/cache/usage` | 측정 대상보다 새로운 워크인지 |
| 라이브러리 전용 testid | 지금 있는 화면의 것 (상세 화면에서는 만족 불가) |
| **조건이 참일 때의 단언** (`if (paired)`, `if (count === 2)`) | **조건이 거짓일 때 무슨 일이 일어나는지** — 규칙이 깨지면 검사가 빨개지는 대신 **사라졌다** (§5.5 3번) |
| **프레임의 bounding rect** | **그 프레임이 실제로 칠해졌는지** — 미디코드 프레임은 폭 0의 보이지 않는 박스인데 rect는 갖는다. desktop-1440에서 스프레드 단언과 리뷰용 스크린샷이 **칠해지지 않은 페이지에 대고 통과**했다 (§5.5 4번) |
| **이전 세션의 인수인계 문장** | **인용된 코드의 지금 상태** — §5.6 항목 4는 그 사이에 생긴 테스트를 몰랐고, 문서 mtime이 테스트 mtime보다 나중인데도 이월됐다 |
| **`workers = 2`로 만든 바쁜 스냅샷** | **두 필드가 서로 다른 값이 되는 상태** — `active == inflight == 2`라 **전치해도 전부 그린**이었는데 테스트 이름은 `separate…`였다 (§5.6.1 F, 이번 세션에 닫힘) |
| **`covers_done == covers_total`** | **파일이 최종 이름으로 디스크에 있는지** — `done`은 큐 깊이에서 유도되므로 디코딩 중인 것이 이미 done이다. `36/36`일 때 파일은 32~33개였다 (§5.6 항목 1) |
| **돌린 게이트들의 결과** | **돌리지 않은 게이트가 있다는 사실** — `make e2e-synthetic`은 세 세션 동안 "전 게이트 그린" 보고 뒤에서 조용히 깨져 있었다. 아무도 실행하지 않았으므로 아무 검사도 실패하지 않았다 (§4.3 / §5.6.1 G) |
| **`[ "$a" = "$b" ]`가 참이라는 것** | **`$a`와 `$b`가 무언가를 담고 있는지** — AC-005의 새 "name for name" 검사가 `?limit=500`(상한 200)으로 400을 받아 양쪽이 빈 문자열이 됐고, `set -e`가 꺼져 있어 `PASS`를 찍었다. **§6.5를 없애려고 넣은 코드가 §6.5가 됐다** (§4.4) |
| **`$?` — 파이프를 거친 뒤의** | **`make` 자신의 종료코드** — `make test \| tail -12; echo $?`는 `tail`의 rc다. 하마터면 검증되지 않은 그린을 출하할 뻔했다 (§6) |
| **`wait_for_idle`이 0을 반환했다는 것** | **잴 대상이 애초에 시작했는지** — 8단계는 `POST /api/scan`이 실패해도 즉시 idle을 보고 `0s < 30s`로 통과한다. 재스캔 없이 재스캔 예산을 인증한다 (§5.6.1 **H**, 열림) |
| **골든 파일이 응답과 일치한다는 것** | **그 응답이 값을 담고 있는지** — 골든은 `"config_path": ""`를 경로만큼이나 기꺼이 고정한다. 실제로 그럴 뻔했고, non-empty + `filepath.IsAbs` 단언만이 반대했다. 하네스가 이미 절대경로를 주므로 **상대경로 케이스를 따로 두지 않으면 절대화 자체가 검사되지 않는다** (§5.6.1 I, 4세션차에 닫힘) |
| **`toHaveCount(0)`이 통과한다는 것** | **왜 0인지** — "컨트롤이 제거돼서 0"과 "기능 게이트가 꺼져 있어서 0"을 구별하지 못한다. A-11의 e2e는 이제 `root_editing_enabled`가 그 라운드의 설정과 같다는 것을 **함께** 단언한다. 결과만이 아니라 이유를 고정할 것 (§4.6) |
| **`201`을 받았다는 것** | **파일이 실제로 바뀌었는지** — 쓰기 API에서 상태코드는 증거가 아니다. `AddRoot`를 통째로 들어내도 201은 그대로 나온다. e2e는 디스크의 바이트와 `.bak`을 본다 (§4.6) |
| **가드를 검사하는 테스트가 없다는 지적** | **그 가드가 애초에 옳은지** — 제거집합의 두 번째 가드는 검사가 없던 게 아니라 **틀린 것**이었고, 검사를 붙였으면 결함을 고정했을 것이다. 리뷰 지적을 받으면 "이걸 어떻게 검사하지"보다 **"이게 맞나"** 를 먼저 물을 것 (§1.2) |
| **655개 유닛이 전부 그린이라는 것** | **그 DOM이 브라우저에서 눌리는지** — 바에 붙인 `z-[3]`이 상단 바를 stacking context로 만들어 그 안의 `⋯` 시트가 하단 바 밑으로 깔렸다. jsdom은 히트테스트를 하지 않으므로 유닛은 전부 통과했고, **mobile-400의 Playwright만** 잡았다. 위의 `jsdom + css:false` 행과 같은 병인데 원인이 달랐다(CSS가 아니라 쌓임 순서). 유닛으로 되돌아오는 길은 클래스 목록 파싱뿐이다 (§1, 5세션차) |
| **MSW가 stderr에 에러를 찍었다는 것** | **테스트가 빨개졌는지** — `msw/node`의 `onUnhandledRequest: 'error'`는 *요청*을 실패시키지 *테스트*를 실패시키지 않는다. "닫혀 있는 동안 쿼리를 마운트하지 않는다"는 테스트가 `useSettings()`를 실제로 추가해도 596/596 그린이었다. 유일한 실단언은 패널 제목이었다 — 지키겠다는 것 **옆의** 것 (§5.6.1 I, 4세션차에 닫힘) |

전부 **그린을 냈다.** 같은 게이트를 다시 돌려서는 절대 드러나지 않는다.
마지막 줄은 한 걸음 더 나아간다: **존재하지만 실행되지 않는 게이트는 그린조차 내지 않는다 —
아무 말도 하지 않는데, 요약은 그것을 침묵이 아니라 동의로 읽는다.**

**적용법**: 게이트를 볼 때마다 "이 검사가 읽는 산출물이 정확히 무엇이고, 그게 사용자가 받는 것인가?"를
물을 것. 플래그·설정·캐시된 값·다른 화면·모의 DOM을 읽는 검사는 전부 의심 대상이다.
그리고 **테스트를 뮤테이션하라** — 검사가 애초에 실패할 수 있는지는 그것으로만 증명된다.

3세션차가 더한 세 가지 따름 규칙:

1. **단언을 조건 안에 넣지 말 것.** 전제조건이 참인지 확신할 수 없으면, 건너뛰는 대신 **전제조건을
   단언하라**. `if (count === 2) { …기하 검사… }`는 짝짓기가 깨지는 순간 커버리지를 0으로 만든다.
   `await expect(frames).toHaveCount(2)` 뒤에 같은 검사를 두면 그 순간이 실패가 된다.
2. **기하를 재기 전에 칠해졌는지 물을 것.** `getBoundingClientRect()`는 보이지 않는 요소도 답한다.
   프론트엔드 E2E에서 좌표·크기·스크린샷을 단언하기 전에 `data-status="ready"` 같은 **도색 완료
   신호**를 전제조건으로 걸 것.
3. **인수인계 문서도 검사다. 인용한 파일보다 오래됐으면 다시 확인할 것.** 이 문서의 §5.6 두 항목이
   그렇게 틀렸다. git이 없으므로 `ls --time-style=full-iso`로 mtime을 비교하는 것이 유일한 단서다.
   같은 이유로 **문서 사이의 행 번호 인용은 못 버틴다** — 이 문서는 세션마다 재작성된다. 무엇을
   가리키든 §번호와 이름으로 가리킬 것.

**기법 하나 — `css: false`인 tier에서 CSS 조건을 단언하는 법.** jsdom + `css: false`는 계산 스타일을
무의미하게 만들지만, **클래스 목록 자체는 진짜다.** `library.test.tsx`가 이 세션에 그 방식으로 오버레이
불변식을 고정했다: 요소의 className을 변형 접두사(`group-hover:` 등)로 파싱해 ① 스크림을 무장시키는
변형이 **하나도 없고** ② 두 버튼의 무장 게이트 집합이 오버레이를 **드러내는** 게이트 집합과 정확히
같음을 단언한다. 히트테스트는 여전히 실제 브라우저의 몫이지만(§5.6 항목 4), "보이게 하는 조건과
누를 수 있게 하는 조건이 갈라지지 않는다"는 성질은 이걸로 유닛 tier에서 잡힌다.

## 7. 이 프로젝트의 작업 방식 (사용자 지정)

- 오케스트레이터 컨텍스트를 아끼기 위해 **서브에이전트에 최대한 위임**한다. 파일 내용이 아니라 경로와 요약을 주고받는다.
- 분석·설계·구현은 opus, 스크립트 실행 같은 단순 작업은 haiku.
- **구현자와 리뷰어는 반드시 다른 에이전트.** 수정 적용도 제3의 에이전트가 한다.
- 리뷰어에게는 "구현자 보고서는 증거가 아니라 주장"이라고 명시하고, **/tmp 사본에서 구현을 일부러 망가뜨려 테스트가 실제로 빨개지는지** 확인시킨다. 이 절차가 이번 빌드에서 가장 많은 실제 결함을 잡았다.
- **수정 에이전트에게도 같은 말을 한다: "리뷰 지적도 주장이다."** 파일에 대고 검증하고, 반증되면 적용하지 말고 **반증했다고 보고**하게 한다. 3세션차에 §5.6 네 항목 중 둘이 그렇게 반증됐다 — 그중 하나는 이 문서 자신의 문장이었다.
- **에이전트를 병렬로 돌릴 때는 각자에게 자기 파일 목록·자기 스크래치 디렉터리·자기 포트를 준다.** 그리고 **저장소에 파일을 남기지 말라**고 명시한다(`PYTHONDONTWRITEBYTECODE=1`). `scripts/e2e.sh` 9단계가 `data_dir`/`cache_dir` 밖의 새 파일에서 실패하고, 그 검사는 옳다.
- 프론트엔드는 **반드시 실제 브라우저에서 렌더링해 측정**시킨다. 유닛테스트가 전부 통과하는데 화면이 완전히 깨져 있던 사례가 여러 건 있었다.
- 테스트 중 **비슷한 유형의 오류·동작이 5번 연속 반복되면 비상중지**한다. 워크플로 스크립트에 실패 클래스 슬러그 기반으로 구현해 두었다 (`shelf-wave4` 스크립트 참조).
- 수정 에이전트에게 "테스트를 약화시키거나 허용오차를 넓혀 통과시키지 말 것, 못 고치면 못 고쳤다고 보고할 것"을 매번 명시한다.
