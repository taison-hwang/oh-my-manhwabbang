# E-74 U-R1 — uni-auth 클라이언트 등록과 Cloudflare 터널의 실제 환경 확인

결론: 터널·Hydra·zip-viewer 환경은 읽기 전용으로 확인했다. **클라이언트 등록은 실행하지 못했다.** 관리 API가 `deploy/.env`의 `GATEWAY_ADMIN_API_TOKEN`을 거부한다(401). uni-auth는 쓰기를 하지 않았다. 터널·DNS·`:9909`도 건드리지 않았다.

검증 표기: **[실행]** 명령을 돌려 확인, **[추론]**, **[미확인]**.

## 1단계 — 읽기 전용 확인

## 2단계 — 클라이언트 등록: **실행하지 않음**

사유: 관리 API 토큰이 401(위 b). 값 자체는 분명해서, 아래 JSON은 토큰이 풀리면 그대로 보낸다.

**client_id 결정: `zip-viewer`.** 근거 — 기존 `ohmyassets`는 제품 이름이고(호스트 라벨과 우연히 같음), 계약 초안의 설정 예시(`client_id: "zip-viewer"`)가 이미 이 값이다. `client_id`는 변경 불가인데 호스트(`library`)는 바뀔 수 있어 제품 이름이 안전하다. `library`로 바꾸려면 계약 초안 한 줄을 고쳐야 한다.

배정문과 다른 점 하나: scope. 배정문은 `"openid"`지만 기존 관례·기본값은 `openid offline_access`다. `offline_access`가 없으면 refresh token이 발급되지 않는다. 계약 초안의 Q3 추천은 (S2) refresh token을 쓰지 않는 안이라 지금은 필요 없지만, 클라이언트 scopes는 허용 집합일 뿐 요청해야 발급된다. 나중에 PATCH(`revision` 증가·재투영) 없이 S3를 열 수 있도록 기본값을 권한다. **결정이 필요하면 `["openid"]`로 바꿔 보내면 된다.**

```json
{
  "client_id": "zip-viewer",
  "name": "SHELF (zip-viewer)",
  "redirect_uris": ["https://library.betterax.net/api/auth/oidc/callback"],
  "post_logout_redirect_uris": ["https://library.betterax.net/"],
  "audiences": ["https://library.betterax.net/api"],
  "scopes": ["openid", "offline_access"],
  "client_uri": "https://library.betterax.net",
  "dev_mode": false
}
```

(`base_path`가 비어 있어 콜백에 접두사가 없다. grant_types·response_types·token_endpoint_auth_method는 서버가 고정하므로 요청에 넣지 않는다. 비밀값 없음.)

실행할 명령(토큰이 풀린 뒤, `uni-auth` 저장소에서):

```bash
. deploy/scripts/admin-helpers.sh
T="$(docker compose -f deploy/compose.yaml -f deploy/compose.dev.yaml -f deploy/compose.prd.yaml exec -T gateway printenv GATEWAY_ADMIN_API_TOKEN)"; export GATEWAY_ADMIN_API_TOKEN="${T%%,*}"; unset T
gateway_admin /admin/api/v1/clients/zip-viewer -o /dev/null -w '%{http_code}\n'   # 404 여야 한다
gateway_admin /admin/api/v1/clients -X POST -d '<위 JSON>'                          # 201
gateway_admin /admin/api/v1/clients/zip-viewer/projection | jq                      # projection_state=ok, projected_revision=revision
hydra_admin /admin/clients/zip-viewer | jq                                          # 저장값 대조
unset GATEWAY_ADMIN_API_TOKEN
```

대조할 값: `redirect_uris`·`post_logout_redirect_uris`·`audience`·`scope`·`grant_types=[authorization_code,refresh_token]`·`response_types=[code]`·`token_endpoint_auth_method=none`.

## 3단계 — 터널 적용 계획 (지금 적용하지 않음)

공개는 oidc 모드 서버 검증 뒤. 형태는 **로컬 설정 관리형**이라 대시보드 작업은 DNS 한 줄뿐이다.

1. **백업:** `sudo cp -p /etc/cloudflared/config.yml /etc/cloudflared/config.yml.bak-$(date -u +%Y%m%dT%H%M%SZ)` (기존 백업 이름 관례와 같다).
2. **ingress 추가:** ohmyassets 규칙 뒤, catch-all 앞에 넣는다. `<주소>`는 oidc 인스턴스가 떠 있는 곳으로, 지금은 정해지지 않았다. 제안은 `127.0.0.1:9910`(`:9909` 사용자 인스턴스와 분리, 공개 인스턴스는 루프백에만 바인드).
   ```yaml
     - hostname: library.betterax.net
       service: http://127.0.0.1:9910
       originRequest:
         httpHostHeader: library.betterax.net
         connectTimeout: 10s
   ```
   규칙 순서는 첫 일치 우선이다. 호스트명이 정확히 구분되므로 auth·ohmyassets 규칙과 겹치지 않고, 마지막 catch-all 404만 그대로 맨 끝에 둔다.
3. **검증(적용 전, 수정한 사본에서):**
   `cloudflared tunnel --config /etc/cloudflared/config.yml ingress validate` → OK
   `cloudflared tunnel --config /etc/cloudflared/config.yml ingress rule https://library.betterax.net/api/auth/oidc/callback` → 새 규칙
   `… ingress rule https://auth.betterax.net/` → 기존 규칙 그대로, `… ingress rule https://ohmyassets.betterax.net/` 동일, `… ingress rule https://other.betterax.net/` → 404.
   (`--config`를 빼면 홈 사본을 검증해 의미가 없다.)
4. **DNS:** 이 기계에서 `cloudflared tunnel route dns gift4me-tunnel library.betterax.net`(cert.pem 사용, **[미확인]**) 또는 대시보드 → DNS에서 `library` CNAME → `178647b8-b76b-49a3-8b8f-3ca06f191226.cfargotunnel.com`(프록시 켬). DNS를 먼저 만들면 서버가 없는 사이 404가 나가므로 **서버 검증 뒤, ingress 적용 직전**에 만든다.
5. **적용:** `sudo systemctl restart cloudflared`(또는 `reload`가 없다). **재시작하면 같은 cloudflared가 서빙하는 `auth.betterax.net`·`ohmyassets.betterax.net`이 몇 초 끊긴다**(연결 4개 재등록, 명시적 시간은 **[미확인]**). cloudflared는 로컬 ingress를 SIGHUP로 다시 읽지 않는다고 알고 있다(**[추론]**, 문서로 확인하지 않음). 무중단 방법은 확인하지 못했다. 같은 터널에 두 번째 connector를 새 설정으로 띄우면 두 설정이 섞여 일부 요청이 404가 되므로 권하지 않는다. uni-auth 로그인 중인 사용자가 적은 시간대에 한다.
6. **적용 후 확인:** `systemctl status cloudflared`·`journalctl -u cloudflared -n 30`에서 `Registered tunnel connection`, 그리고 `curl -sI https://auth.betterax.net/.well-known/openid-configuration`·`https://ohmyassets.betterax.net/`가 이전과 같은 응답인지, `https://library.betterax.net/`가 oidc 인스턴스에 닿는지.
7. **되돌리기:** `sudo cp -p /etc/cloudflared/config.yml.bak-<백업 이름> /etc/cloudflared/config.yml && sudo systemctl restart cloudflared`. DNS 레코드는 남겨도 catch-all이 404를 준다. 지우려면 대시보드에서 `library` CNAME 삭제.

공개 전 선행 조건(코드·검증): oidc 모드 구현(계약 초안), 우회 경로 점검(`:9909` 평문 경로가 공개 인스턴스와 같은 데이터 디렉터리를 쓰지 않을 것, `trusted_proxy_headers` 끔), 클라이언트 등록 완료.

## 막힌 것과 필요한 결정

1. **관리 API 토큰 401.** 필요한 것 하나: 실행 중 게이트웨이의 실제 토큰을 쓰는 것에 대한 승인(`docker compose … exec -T gateway printenv GATEWAY_ADMIN_API_TOKEN`, operations-guide.md:530이 정한 운영 절차) 또는 사용자가 직접 위 등록 명령 실행.
2. scope를 `openid`만 할지 `openid offline_access`로 할지(위 설명).
3. `:9909`가 지금 꺼져 있다는 사실을 Commander에게 알린다(의도한 상태인지 모름).

  - client_name `SHELF (zip-viewer)`, redirect_uris `["https://library.betterax.net/api/auth/oidc/callback"]`, audience `["https://library.betterax.net/api"]`, scope `openid offline_access`, grant_types `["authorization_code","refresh_token"]`, response_types `["code"]`, token_endpoint_auth_method `none`, skip_consent true, allowed_cors_origins `[]`, client_uri `https://library.betterax.net`, metadata `{rev:1}` → 요청과 일치하고 기존 `ohmyassets`와 같은 모양이다.
  - **불일치 1건:** `post_logout_redirect_uris`가 게이트웨이 레코드에는 `["https://library.betterax.net/"]`인데 Hydra 쪽은 `null`이다. 기존 클라이언트는 모두 비어 있어서 투영기가 이 필드를 Hydra로 보내는지 이전에는 관찰할 수 없었다. **[추론]** 투영기가 이 필드를 투영하지 않는다. 가이드는 로그아웃 리다이렉트 화이트리스트가 강제된다고 하므로(integration-guide.md:127) "모든 서비스에서 로그아웃" 뒤 복귀가 인증 서버 화면에 머물 수 있다. **[미확인]** end-session은 조율 레이어(`end_session_endpoint`)가 처리하므로 실제로 영향이 있는지는 로그아웃을 시도해 봐야 안다(금지 범위라 하지 않음). uni-auth 쪽 확인이 필요한 열린 문제로 남긴다.
