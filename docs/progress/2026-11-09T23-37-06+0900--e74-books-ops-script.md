| 지적 | 고친 동작 |
| --- | --- |
| I1 `tunnel restart`에 설정 거부가 없음 | `tunnel apply`와 같은 preflight 관문. 불안전 설정이면 cloudflared를 재시작하지 않고 종료 3 |
| I2 상대 `--config` + 다른 `--workdir`이면 검사한 설정과 실행한 설정이 다름 | 모든 경로 옵션(`--config`·`--bin`·`--workdir`·`--state-dir`·`--cf-config`)을 실행한 디렉터리 기준 절대 경로로 먼저 확정한다. 검사·백업·실행이 같은 파일을 쓴다 |

| I4 되돌릴 ingress 백업이 없어도 `tunnel restart`가 진행 | `tunnel apply`가 기록한 백업이나 `--backup F`가 있어야 하고, 그 파일의 ingress가 `books.betterax.net`을 어떤 서비스로도 보내지 않아야 한다. 아니면 재시작 전에 거부(종료 1) |
| I4 재검증: 백업 검사가 `grep "hostname: *books…"`라 `hostname: "books.betterax.net"` 같은 동등 표기의 백업을 받아들임 | 백업과 현재 설정을 YAML로 읽어 cloudflared의 규칙 판정대로 본다(`books_proc.py routes`): 규칙을 위에서부터, hostname은 대소문자 무시·끝 점 무시·`*.` 와일드카드·hostname 없음(=모든 호스트)으로 맞추고, `http_status:`가 아닌 서비스로 가면 "보낸다". `path`가 붙은 규칙은 일부 요청만 보내도 보낸다로 친다. 따옴표·작은따옴표·대문자·flow 표기·와일드카드·서비스로 가는 catch-all이 모두 같은 판정이다. ingress를 읽을 수 없는 파일도 거부한다 |
| I4 재검증: 롤백 뒤 확인 없이 "404 again" 안내 | 롤백 뒤 현재 설정이 여전히 books를 보내면 `ROLLBACK INCOMPLETE`, 아니면 공개 URL을 최대 5번(2초 간격) 확인해 실제로 404일 때만 "answers 404 again". 아니면 받은 코드와 `books.sh status` 안내 |
| I5 `init`이 확인 없이 파일을 만듦 | 다른 변경 단계처럼 대화형 `yes` 또는 `--yes`가 필요하다(없으면 종료 10) |

## 안전 장치 (스크립트가 강제하는 것)

| 조건 | 동작 |
| --- | --- |
| `auth.mode`≠oidc, `listen` 비루프백, issuer·client_id·audience·redirect_url이 books 등록값과 다름, `trusted_proxy_headers` 켬, password 동시 설정 | `start`·`restart`·`tunnel apply`·`tunnel restart`·`check`가 preflight FAIL로 **아무것도 바꾸지 않고 종료 3** |
| 바이너리가 설정을 거부함(위 I3) | `check`·`restart`가 종료 3. `restart`는 기존 프로세스를 멈추지 않는다 |
| 같은 data_dir의 파일을 연 프로세스(옛 `:9909` shelf 등)가 있음 | `start` 거부(종료 4), 그 pid와 명령줄 출력 |
| `start` 직전 | data_dir 전체를 `<data_dir>.bak-<UTC>`로 복사(아래 "백업 범위"). 백업·데이터는 지우지 않는다 |
| 기동 뒤 헬스(`/api/health` 200, `--wait` 초) 또는 로컬 verify FAIL | 새 인스턴스를 TERM, pidfile 삭제, 로그·백업·직전 정상 설정 경로 출력(종료 5) |
| `stop` | pidfile의 pid가 살아 있고, 명령줄이 `--bin`·`--config`과 일치하고, 설정 포트의 주인일 때만 TERM. 하나라도 다르면 종료 6. 15초 안에 안 끝나도 KILL하지 않는다 |
| `tunnel apply` | 실행 중 인스턴스의 로컬 verify가 FAIL 0일 때만 `sudo tunnel-apply.sh`(백업·검증·실패 시 복원). cloudflared는 재시작하지 않는다 |
| `tunnel restart` | preflight·로컬 verify·복구용 백업 확인(존재하고 ingress가 books를 보내지 않음, 위 I4) → `sudo systemctl restart cloudflared` → 활성 확인 → 공개 verify. 실패하면 백업으로 되돌리고 다시 재시작(종료 8). 되돌린 뒤 현재 설정과 공개 URL을 확인하고, 확인된 경우에만 "404 again"이라고 쓴다 |
| ingress에 books 규칙이 있는가(`tunnel apply`의 "이미 있음", `tunnel restart`의 "먼저 apply", `status`) | 위와 같은 YAML 판정. 따옴표로 쓴 규칙도 적용된 것으로 본다 |
| 확인 | `init`·`start`·`stop`·`restart`는 대화형 `yes` 또는 `--yes`. sudo 단계(`tunnel apply`·`tunnel restart`·`rollback`)는 대화형 `sudo` 또는 `--yes-sudo`로 **따로**(`--yes`로는 안 된다). 확인이 없으면 종료 10 |
| `--dry-run` | 검사만 하고 바꿀 일을 `>> would:`로 출력 |
| 설정 파일 | 쓰지 않는다. `init`만 새 파일을 만들고, 대상이 있으면 거부(종료 9) |

**스크립트가 지우는 것.** pidfile(인스턴스를 멈출 때)과 바이너리 설정 검사가 `mktemp -d`로 만든 자기 임시 폴더(`$TMPDIR/books-check.*`, 사본 설정·임시 data_dir·로그)뿐이다. 사용자 데이터·백업·설정은 지우지 않는다.

**백업 범위.** data_dir 전체(`index.db`·`user.db`·`auth.db`·`session.key`와 `-wal`·`-shm`). [실행] 지금 운영 data_dir `resources/shelf`는 169,783,296 B(대부분 `index.db` 168,669,184 B), 그 파일 시스템의 여유는 약 1.69 TB라 범위를 줄이지 않는다. 여유가 크기의 2배보다 작으면 `start`가 아무것도 바꾸지 않고 멈춘다. cache_dir(썸네일 캐시)은 다시 만들 수 있어 백업하지 않는다. 백업은 쌓이며 정리는 사용자가 한다.

## 사용 절차 (§5 A~F 대체)

```bash
cd /mnt/data/codejobs/projects/betterax-proto/zip-viewer
B=scripts/deploy/library/books.sh          # 기본값: --config ./shelf.books.yaml --bin ./dist/shelf --workdir .
```

1. **설정 만들기(한 번)** — `$B init --from shelf.yaml`(대화형 `yes`, 또는 `--yes`). `shelf.yaml`을 읽어 `server`를 `127.0.0.1:9910`으로, `auth` oidc 블록(books 값)을 넣은 **새** `shelf.books.yaml`을 쓴다. 원본 주석은 옮기지 않는다. `server.allow_root_editing`은 원본 값(지금 `true`)을 유지하므로 공개 서버에서 끌지 직접 정한다.
2. **점검** — `$B check`. 기대: preflight 표 `FAIL 0`(P6 allowed_subs 빈 값 WARN), `>> binary config check: … accepts …`, `>> check: no FAIL`. 바이너리 검사는 사본을 임시 포트에 수 초 띄웠다 끈다(실제 data_dir·포트는 건드리지 않는다). 옛 `:9909`가 `0.0.0.0`에서 돌고 있으면 P14 FAIL이 정상이다(3단계 뒤 FAIL 0).
3. **옛 `:9909` 서버 중지(사용자, 스크립트 밖)** — `books.sh`가 띄운 서버가 아니라서 `stop`이 끄지 않는다. 띄운 방식대로 멈춘다(`ss -ltnp | grep :9909` → `kill <PID>`). 멈추지 않으면 4단계가 종료 4로 거부한다.
4. **기동** — `$B start`(`yes`/`--yes`). 기대: `>> backup: …/resources/shelf.bak-<UTC>`, `>> started pid N`, verify 표 `FAIL 0`, `>> running: pid N on 127.0.0.1:9910`. 실패면 새 인스턴스는 이미 멈췄고 "recovery:" 줄이 로그·백업·직전 정상 설정을 가리킨다.
5. **ingress 적용(sudo)** — `$B tunnel apply`(`sudo`/`--yes-sudo`). 기대: tunnel-apply 표 T1~T5 PASS, `>> ingress rule added (backup /etc/cloudflared/config.yml.bak-<UTC>)`. 재시작 전이라 아직 공개되지 않는다.
6. **cloudflared 재시작(sudo, 수 초 중단)** — 시간을 골라 `$B tunnel restart`. **같은 터널의 `auth.betterax.net`·`ohmyassets.betterax.net`이 몇 초 끊긴다**(stock·ssh는 다른 터널). 5단계가 기록한 백업을 복구용으로 쓴다. 5단계를 수동으로 했다면 `$B tunnel restart --backup /etc/cloudflared/config.yml.bak-<UTC>`. 기대: 공개 verify 표 FAIL 0, `>> public: https://books.betterax.net passes verify`. 실패하면 백업으로 되돌리고 다시 재시작한다(종료 8). 마지막 줄이 `rolled back; … answers 404 again`이면 확인된 것이고, `ROLLBACK INCOMPLETE`·`answered <코드>, not 404`면 `$B status`로 보고 `$B rollback --backup …`을 다시 한다.
7. **첫 로그인과 허용 목록** — `https://books.betterax.net/` → `uni-auth로 로그인` → 첫 로그인은 403 화면이 정상, 화면의 `sub`를 복사한다. `shelf.books.yaml`의 `auth.oidc.allowed_subs`(필요하면 `admin_subs`·`legacy_owner_sub`)에 **직접** 넣고 `$B restart`. 스크립트는 설정을 고치지 않고, 새 설정을 검사한 뒤 다시 띄우기만 한다.

상태는 언제든 `$B status`(읽기 전용). 공개 중단은 `$B rollback`(sudo), 서버 중지는 `$B stop`.

## 위험·열린 문제

- 바이너리 설정 검사의 사본은 data_dir·cache_dir·포트·`scan.on_start`를 바꾸므로, 그 네 값에서만 생기는 오류(예: 실제 data_dir 쓰기 권한)는 실제 기동에서야 드러난다. `restart`에서 그렇게 실패하면 옛 프로세스는 이미 멈춘 뒤이고, 스크립트는 새 인스턴스를 멈추고 직전 정상 설정(`<state>/last-good.yaml`)으로 다시 띄우는 명령을 출력한다 [추론: 이 경로를 실제 바이너리로 돌리지 않았다].
- 바이너리 검사는 실제 roots를 그대로 둔 사본을 띄운다(스캔 없음). shelf가 기동 때 roots에 하는 일은 읽기뿐이다(FR-CFG-005) [추론].
- `books.sh`로 띄운 서버는 `nohup` 백그라운드 프로세스라 재부팅 뒤 다시 `start`해야 한다(systemd 단위는 범위 밖).
- `tunnel-apply.sh`를 `books.sh` 없이 직접 부르면 그 안의 "이미 있음" 검사는 여전히 grep이라, 따옴표로 쓴 books 규칙이 있는 설정에 규칙을 하나 더 넣는다. cloudflared는 첫 규칙을 쓰므로 공개 범위는 바뀌지 않는다 [추론]. `books.sh tunnel apply`는 YAML 판정을 먼저 하므로 이 경로를 타지 않는다 [실행: 테스트의 따옴표 현재 규칙 경우].
- 롤백 뒤 404 확인은 최대 5번 시도하고, 시도마다 응답을 최대 10초 기다린 뒤 2초 쉰다(`books.sh` `report_unpublished`). 최악이면 약 1분(5×(10+2)초) 걸린다 [실행: 재검증이 1.2초 지연 서버로 16.1초를 실측, `/tmp/verify-ur4/round3/timing.log`]. 그동안 404가 확인되지 않으면 "not 404"로 보고하며, 그때는 `books.sh status`로 다시 본다.
- 로그아웃 복귀(Hydra `post_logout_redirect_uris` null)는 U-R3b 기록의 열린 문제 그대로.
