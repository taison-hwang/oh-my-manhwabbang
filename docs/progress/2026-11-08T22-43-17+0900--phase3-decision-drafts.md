# prd §9 3차 로드맵 여덟 기능 판정 초안 (검토용, 미확정)

이 문서는 초안이다. 번호 E-70~E-77과 개정 A-20~은 가번호이고 확정할 때 다시 매긴다. 사용자가 기능별로 확정하기 전에는 `docs/decisions.md`·prd·intent·arch·코드 어느 것도 바뀌지 않는다(intent.md:27-28, E-67 §2.2 = decisions.md:4280-4281). 앞선 기록: [phase3-roadmap-decision](2026-11-08T22-37-15+0900--phase3-roadmap-decision.md).

읽는 법: "직접 충돌"은 그 기능을 하면 문구가 틀려지는 요구사항·경계다. "판정에서 검토"는 설계로 맞출 수 있지만 판정에 답을 적어야 하는 항목이다(E-67과 같은 구분). 인용은 2026-11-08 `main` 0461718 기준 `파일:행`이다. 수치 옆의 "추정"은 측정하지 않은 값이다.

공통 직접 충돌: E-73~E-77 다섯은 intent.md:39 "3차 로드맵 다섯 기능(판정 전)"에 걸린다. 이 줄은 판정 자체로 풀리는 조건이라 위 표의 수에는 넣지 않았다. E-70~E-72 셋은 E-67 표(decisions.md:4283-4289)에 없다. 그 셋의 근거는 intent 경계와 impl-plan §1.3 OUT 표(impl-plan.md:274·276·277)다.

D-02 처리: D-02는 "stage 3 only where trivially free"다(decisions.md:17). E-67은 이를 근거로 다섯 기능을 범위 밖에 두었다(decisions.md:4278). E-70~E-72도 intent 경계 변경(사용자 승인)이 필요하므로 trivially free가 아니다. arch가 모양을 이미 적어 둔 E-72 최소안(arch-backend.md:3300)조차 경계 한 칸을 바꿔야 한다. 그래서 여덟 기능 모두 범위에 넣는 근거는 D-02가 아니라 사용자 지시다. E-68이 같은 방식을 썼다(decisions.md:4319).

공통 사실(직접 확인):
- 릴리스 크기 예산 여유는 33 554 432 − 33 210 530 = **343 902 B**다(Makefile:115 `SIZE_BUDGET`, Makefile:138 `MEASURED_DEFAULT`, go1.26.9 기준).
- 고정 의존성은 10개이고 늘리면 D-08(decisions.md:32)과 `FROZEN_DEPS`가 함께 바뀐다. intent는 새 런타임 의존성 추가와 예산 상향을 사용자 승인 항목으로 둔다(intent.md:30).
- contractcheck는 `docs/decisions.md`가 아니라 `docs/arch-backend.md`와 `docs/impl-plan.md` §0.3의 `AMENDMENT A-n`을 대조한다(scripts/contractcheck/main.go:1075-1079). 그래서 A-20~을 확정할 때는 impl-plan §0.3 행을 먼저 넣고 arch에 같은 번호의 표시를 둬야 검사가 통과한다. 이 초안은 그 두 파일에 없으므로 검사에 걸리지 않는다.
- user.db 이전 규칙: 새 단계는 `CREATE TABLE IF NOT EXISTS`·`CREATE INDEX IF NOT EXISTS`만 할 수 있다(arch-backend.md:917-918). 기존 테이블의 키를 바꾸는 기능은 이 규칙부터 바꿔야 한다.

## E-70 — 모바일 제스처 최적화 (가번호)

### 1. 범위
- **최소안:** 뷰어 단면·양면 모드에 핀치 줌, 확대한 상태의 한 손가락 팬, 더블탭 확대/복귀를 더한다. 확대 중에는 가로 스와이프가 페이지를 넘기지 않고 화면을 옮긴다. 클라이언트만 바뀐다.
- **확장안:** 최소안 + 세로(웹툰) 모드 관성 스크롤 조정, 화면 가장자리 스와이프(뒤로 가기), 스와이프 감도 설정을 설정 화면에 둔다.
- **하지 않는 것:** 서버 리사이즈·화면 크기별 이미지(FR-SRV-008, prd.md:123), 네이티브 앱, 탭 영역 배치 변경(E-28이 정한 것).

### 2. 충돌
- **직접 충돌:** intent 경계 "하지 않는다: … 모바일 제스처 최적화"(intent.md:39). impl-plan §1.3 OUT 행(impl-plan.md:276)도 같은 내용이다.
- **판정에서 검토:**
  - prd와는 충돌하지 않는다. 기본 터치는 FR-VWR-011(권장, prd.md:168)로 이미 들어와 있고, NFR-CMP-002(prd.md:220)는 태블릿·모바일 레이아웃을 요구한다. 대상 사용자도 모바일을 "부"로 둔다(intent.md:12).
  - 제스처 우선순위: 현행 규칙은 가운데 36% 탭이 크롬 토글, 가로 스와이프가 ≥44px·600ms 안의 페이지 넘김이다(ui-spec.md:1914-1915, E-28 = decisions.md:655). 확대 상태에서 스와이프의 뜻을 정해야 한다.
  - 원본 크기 맞춤(FR-VWR-005, prd.md:162)과 줌 배율의 관계.
  - 핵심 가치 1~5와 충돌 없음. 확대는 원본 바이트(FR-SRV-008)를 그대로 쓰므로 오히려 맞는다.

### 3. 대안
| 대안 | 내용 | 바꿀 문서 |
| --- | --- | --- |
| (a) 하지 않음 | 탭 영역 + 가로 스와이프 유지 | 없음 |
| (a') 실기기 확인 먼저 | 브라우저 기본 핀치 줌이 이미 되는지 태블릿·폰에서 확인한다. viewport에 `user-scalable=no`가 없고(web/index.html:16), `useTouchZones.ts`에 `preventDefault`·`touchmove`가 없다(grep 0건). 되면 확대 중 스와이프 판정만 고친다 | 확인 기록만. 스와이프 판정을 고치면 ui-spec 뷰어 입력 표(1915) |
| (b) 최소안 | 핀치 줌·팬·더블탭 | intent.md:39 경계에서 "모바일 제스처 최적화" 제거, impl-plan §1.3 행 이동, ui-spec 뷰어 입력 표(1914 부근)에 행 추가 |
| (c) 확장안 | (b) + 관성·가장자리·감도 설정 | (b) + arch §7.8 설정 스키마(A-20), ui-spec 설정 화면 |

### 4. 영향
- 코드: `web/src/features/viewer/useTouchZones.ts`(189행), `web/src/features/viewer/ViewerPage.tsx`. 서버 코드 변화 없음(최소안).
- 스키마·계약: 최소안은 없음. 확장안의 감도 설정을 서버에 두면 user.db `settings`와 arch §7.8이 바뀐다(A-20).
- 크기: 직접 구현이면 SPA 증가 수 KB(추정). 제스처 라이브러리를 넣으면 수십 KB(추정)이고 `web/src/router.tsx:58`은 뷰어에 줌 라이브러리 같은 무거운 의존성이 들어오면 라우트 분할을 다시 보라고 적어 두었다. 343 902 B 여유 안이다(추정).
- 의존성·CGO: 없음.
- 검사: Playwright 터치 에뮬레이션 e2e가 새로 필요하다. contractcheck 영향 없음(최소안).
- 되돌리기: 쉽다(클라이언트만).

### 5. 사용자 결정 질문
1. 코드를 바꾸기 전에 태블릿·폰에서 브라우저 기본 핀치 줌이 되는지 먼저 확인할까? (예/아니오)
2. intent 경계에서 "모바일 제스처 최적화"를 빼고 최소안(핀치 줌·팬·더블탭)을 범위에 넣을까? (예/아니오)
3. 확대한 상태의 가로 스와이프는 화면 이동으로 하고, 페이지 넘김은 배율 1일 때만 할까? (예/아니오)

### 6. 초안 추천
(a') 실기기 확인 먼저, 부족하면 (b) — 브라우저 기본 줌이 이미 될 수 있고, (b)도 요구사항·핵심 가치와 충돌이 없으며 클라이언트만 바뀐다.

## E-71 — 아카이브 포맷 확장 (7z·RAR 5·solid/분할/암호화 RAR) (가번호)

### 1. 범위
하위 항목마다 성격이 다르다.

| 하위 항목 | 핵심 가치 3(한 쪽 = 한 번의 seek)과 |
| --- | --- |
| RAR 5 비solid·단일 파일·비암호화 | 성립한다. D-71의 RAR 4와 같은 접근 모양 |
| 7z 비solid | 성립한다. 다만 7z는 기본 설정이 solid라 실파일 비율을 재야 한다(추정) |
| 분할 볼륨 RAR | 엔트리가 볼륨에 걸치지 않으면 성립한다 |
| solid RAR·solid 7z | **성립하지 않는다.** N쪽에 1..N-1쪽 해제가 필요하다(D-71 근거, decisions.md:24) |
| 암호화 RAR | 비밀번호 보관이 필요하다. 접근 모양과는 무관 |

- **최소안:** RAR 5 비solid·단일 파일·비암호화만 연다. 나머지는 지금처럼 이유를 밝힌 `unsupported`.
- **확장안:** 최소안 + 7z 비solid + 엔트리가 볼륨에 걸치지 않는 분할 RAR 세트.
- **하지 않는 것(두 안 모두):** solid 아카이브(핵심 가치 3), 암호화 아카이브(비밀번호 보관이 새 보안 표면이다. 현행은 이유를 밝힌 `unsupported`로 거부한다, prd.md:331·D-71 decisions.md:24).

### 2. 충돌
- **직접 충돌** (최소안은 앞의 셋 중 RAR 5 부분: intent.md:37·prd.md:331·D-71. 7z 문구(prd.md:333·D-07)는 확장안에만 걸린다):
  - intent 경계 "하지 않는다: 7z, RAR 5, solid·분할·암호화 RAR 열람"(intent.md:37).
  - prd §7.2: "7z과 그 밖의 포맷은 그대로 범위 밖이다"(prd.md:333), "solid·분할볼륨·암호화·RAR 5는 여전히 거부"(prd.md:331).
  - D-71 "refused by name"(decisions.md:24), D-07 "7z … out"(decisions.md:22).
  - solid를 들이면 핵심 가치 3(intent.md:19)과 FR-SRV-002(prd.md:117)에 정면 충돌한다. 최소안·확장안은 solid를 들이지 않으므로 이 둘과는 충돌하지 않는다.
- **판정에서 검토:**
  - 수요: D-71이 잰 실컬렉션 RAR 14개 중 RAR 5는 **0개**였다(decisions.md:24). 7z 파일 수와 solid 비율은 **미측정**이다. D-72는 `.7z`를 `unsupported`로 밝히는 대상으로만 적었다(decisions.md:26).
  - FR-IDX-002(prd.md:101): 헤더만 읽는 스캔. 7z는 헤더가 파일 끝에 있고 압축될 수 있어(추정) 스캔 때 헤더 해제가 필요할 수 있다.
  - FR-SRV-003(권장, prd.md:118): 무압축 엔트리의 Range 전송.
  - CON-001(prd.md:293)과 핵심 가치 5(intent.md:21): 순수 Go여야 한다.
  - 새 의존성은 intent 승인 항목(intent.md:30)이고 D-08 고정 목록(decisions.md:32)을 바꾼다.

## E-73 — 외부 메타데이터 서비스 연동 (가번호)

### 1. 범위
- **최소안:** 시리즈 상세 화면에서 사용자가 버튼을 눌렀을 때만 외부 서비스를 조회하고, 후보 중 하나를 사용자가 고르면 작가·연재 상태·장르를 user.db에 저장해 상세 화면에 보여 준다. 자동 일괄 매칭 없음, 외부 표지 이미지 없음.
- **확장안:** 스캔 뒤 백그라운드 자동 매칭, 작가·장르 검색과 필터, 외부 표지 이미지를 서버에서 받아 캐시에 둔다.
- **대안 안(d):** 외부 서비스 대신 아카이브 안의 메타데이터 파일(예: ComicInfo.xml)을 읽는다. 네트워크가 없다. 실컬렉션에 그런 파일이 있는지 미측정이다. 스캔 때 읽으면 FR-IDX-002 "엔트리 데이터를 압축 해제하지 않아야 한다"(prd.md:101)와 **직접 충돌**한다. 시리즈 상세를 요청할 때 지연해서 읽는 변형은 스캔과 무관해 이 충돌을 피한다.
- **대안 안(e):** 외부 소스 없이 사용자가 직접 입력하는 메타데이터 필드(user.db), 또는 파일명 파싱을 강화해 권수·완결 여부를 뽑는다. prd §7.1 "파일명이 사실상의 메타데이터"(prd.md:322)·§5.1(prd.md:238)과 맞고, NFR-OPS-002와 외부 송신을 건드리지 않는다.
- **하지 않는 것:** 받은 메타데이터로 파일 이름을 바꾸기(E-75 영역), 외부 서비스로의 쓰기.

### 2. 충돌
- **직접 충돌:**
  - prd §7.1 "외부 메타데이터 소스는 없다"(prd.md:322). E-67이 직접 충돌로 적었다(decisions.md:4285).
  - intent "쓰지 않을 사람: … 작가·연재 정보 같은 외부 메타데이터가 필요한 사람"(intent.md:13).
  - intent 경계 "3차 로드맵 다섯 기능(판정 전)"(intent.md:39).
- **판정에서 검토:**
  - NFR-OPS-002 "런타임 외부 의존성은 설정 파일과 캐시 디렉터리 외에 없어야 한다"(prd.md:200)와 같은 문구의 핵심 가치 5 "런타임 의존은 설정 파일과 캐시 디렉터리뿐"(intent.md:21). 외부 서비스가 없거나 꺼져도 모든 기능이 그대로여야 양립한다(E-67 검토 항목). 핵심 가치 5 문구를 정리해야 하는지도 판정에 적는다.
  - 저장 위치: 사용자가 고른 매칭은 사용자가 만든 데이터라 user.db(NFR-DAT-004, prd.md:213; 핵심 가치 2, intent.md:18). 받은 값 자체는 다시 받을 수 있는 파생 데이터(NFR-DAT-001, prd.md:210). 둘을 나눌지 정해야 한다.
  - CSP `img-src 'self' data: blob:`(internal/httpapi/middleware.go:27-28, arch-backend.md:3045): 외부 표지는 브라우저가 직접 받을 수 없어 서버 경유가 필요하다(확장안).
  - 개인정보: 시리즈 이름(파일명)을 제3자 서비스로 보낸다. 외부로 나가는 데이터라 사용자 승인 대상으로 본다(intent.md:31의 취지).
  - prd §5.1 선정 근거 "파일명 자체에 권수·완결 여부 등 메타데이터가 담겨 있다"(prd.md:238)와 가치가 겹친다.
  - 한국 만화 컬렉션에 맞는 소스가 있는지, API 키·이용 약관은 미조사.

### 3. 대안

| --- | --- | --- |
| (a) 하지 않음 | 파일명이 메타데이터 | 없음 |

| (c) 확장안 | 자동 매칭·필터·외부 표지 | (b) + arch §7.5 목록 필터(A-21), §8.4 CSP 또는 표지 프록시, 썸네일 캐시 배치 |

## E-74 — 다중 사용자 계정·권한 (가번호)

### 1. 범위
- **최소안(가족 프로필):** 설정 파일에 사용자 N명(이름 + bcrypt 해시)을 둔다. 로그인하면 그 사용자의 진행률·권별 설정·이어보기·완독만 보인다. 권한 구분은 없다. 설정 쓰기(루트 편집 등)는 지금처럼 설정 파일 플래그로만 연다.
- **확장안:** 최소안 + 역할(관리자/읽기 전용), 루트별 접근 권한(특정 루트를 특정 사용자에게 숨김), 화면에서 계정 만들기·비밀번호 바꾸기.
- **하지 않는 것:** 외부 ID 공급자(OAuth 등), 사용자 자가 가입, 공유·댓글.

### 2. 충돌
- **직접 충돌** (최소안은 앞의 넷, 확장안은 다섯 모두):
  - NFR-SEC-002 "단일 사용자 비밀번호 인증"(prd.md:228).
  - arch §7.12 로그인 계약 `body {password: string}`(arch-backend.md:2968-2975)과 §8.2 세션 토큰(payload에 사용자가 없다, arch-backend.md:3028-3035). E-67이 직접 충돌로 적었다(decisions.md:4286).
  - intent 경계 "하지 않는다: 다중 사용자 계정·권한"(intent.md:40).
  - (확장안) intent "쓰지 않을 사람: 여러 사용자에게 계정을 나눠 서비스하려는 운영자"(intent.md:13). 역할·계정 화면은 이 운영자 모양이다.
- **판정에서 검토:**
  - 최소안과 intent.md:13: 대상 사용자가 "본인 또는 소수 가족"(intent.md:11)이라 가족 프로필은 대상 안쪽일 수 있다. "쓰지 않을 사람"은 서비스 운영자를 겨냥한다. 이 구분을 판정에 적어야 한다.
  - user.db 설계: `progress`의 기본 키는 `book_id` 하나다(arch-backend.md:730-731). 기존 키를 바꾸면 추가만 허용하는 이전 규칙(arch-backend.md:917-918)을 바꿔야 한다. 사용자별 새 테이블(`(user_id, book_id)` 키)을 더하고 기존 `progress`를 기본 사용자 몫으로 읽으면 규칙 안에 들어간다. 판정은 이 추가형 설계를 기본으로 검토한다.
  - FR-STT-001(prd.md:175)·FR-VWR-002(prd.md:159)·FR-STT-004(prd.md:178)를 사용자별로 나누는 방식(E-67 검토 항목). 기존 진행률은 첫 사용자에게 귀속하는 것이 자연스럽다(추정).

## E-75 — 컬렉션 편집 (업로드·이름 변경·삭제) (가번호)

### 1. 범위
- **최소안(표시 편집):** 미디어 볼륨에 쓰지 않는다. 시리즈 숨기기, 표시 이름 바꾸기, "정리 후보" 표시를 user.db에만 저장한다. 실제 파일 정리는 사용자가 파일 관리자로 한다. prd §9의 문구(파일 업로드·이름 변경·삭제)를 채우지는 **못한다** — 요구를 다시 정의하는 안이다.
- **확장안(실제 파일 조작):** 루트마다 `writable: true`를 켠 루트에서만 업로드·이름 변경·삭제를 허용한다. 삭제는 루트 안의 휴지통 디렉터리로 옮긴다. 이름 변경 때 진행률을 새 ID로 옮긴다.
- **하지 않는 것:** 아카이브 내부 수정(엔트리 추가·삭제), 손상 파일 고치기(핵심 가치 4, intent.md:20), 기본값으로 쓰기 켜기.

확장안 기준. 최소안은 아래 "판정에서 검토"만 해당한다.

## E-76 — OPDS 서버 (가번호)

### 1. 범위
- **최소안:** OPDS 1.2 탐색 피드(루트 → 시리즈 → 권)를 읽기 전용으로 낸다. 권은 OPDS 페이지 스트리밍 확장(PSE)으로 기존 페이지 끝점 `/api/books/{bid}/pages/{n}`을 가리킨다. 표지 링크는 기존 표지 끝점. 원본 파일 다운로드는 없다. 기본값은 꺼짐.
- **확장안:** 최소안 + 원본 파일 획득 링크(zip·pdf), 검색(OpenSearch), 진행률 연동(PSE 마지막 읽은 쪽).
- **하지 않는 것:** OPDS를 통한 쓰기, OPDS 2.0 JSON(별도 판정).

### 2. 충돌
- **직접 충돌:**
  - intent "쓰지 않을 사람: … OPDS 리더 사용자"(intent.md:13).
  - intent 경계 "3차 로드맵 다섯 기능(판정 전)"(intent.md:39).
  - prd에는 없다. E-67도 "직접 충돌: 없다"로 적었다(decisions.md:4288).
- **판정에서 검토:**
  - 새 끝점은 HTTP 계약 개정(A-20)이다(E-67 검토 항목). 피드는 JSON이 아니라 XML이라 contractcheck(골든 JSON ↔ types.ts)가 닿지 않는다. 별도 골든 검사가 필요하다.
  - 인증: 현행은 로그인 뒤 세션 쿠키뿐이고 인증은 전부 아니면 전무다(arch-backend.md:2968-2975, 3028-3035). OPDS 리더는 대개 HTTP Basic을 쓴다(추정, 클라이언트별 미확인). Basic을 열면 요청마다 bcrypt(cost 12) 비교가 돌아 페이지 요청이 느려진다(추정 — 검증 결과 캐시나 별도 토큰이 필요). 로그인 시도 제한(IP당 분당 5회, arch §8.2)과의 관계도 정해야 한다.
  - 피드 안 절대 URL과 base path(NFR-SEC-003, prd.md:229).
  - 파일 제공 경로는 NFR-SEC-001(prd.md:227)을 그대로 따른다(인덱스 ID 경유).
  - 확장안의 원본 다운로드: zip·pdf는 원본 그대로 주면 되지만, 폴더형 권은 단일 파일이 없고 HV3는 마스크된 바이트라(E-51, decisions.md:3010) 다운로드로 줄 수 없다.

## E-77 — 이미지 자동 보정 (업스케일·컬러 보정) (가번호)

### 1. 범위
- **최소안(브라우저 표시 보정):** 뷰어가 밝기·대비·채도·감마를 화면 표시에만 적용한다. "자동"은 브라우저가 현재 쪽의 히스토그램으로 자동 대비를 계산하는 버튼이다. 서버는 지금처럼 원본 바이트를 준다.
- **확장안(서버 보정본):** 서버가 업스케일·색 보정한 이미지를 만들어 캐시하고, 새 쿼리 파라미터나 끝점으로 준다. 원본 끝점은 그대로 둔다.
- **하지 않는 것:** 원본 끝점이 보정본을 주는 것, 미디어 볼륨에 보정본 쓰기.

### 2. 충돌
- **직접 충돌(확장안):**
  - 핵심 가치 1 "페이지는 원본 바이트 그대로 준다. 예외는 PDF 래스터화와 썸네일뿐이다"(intent.md:17) — 예외 목록에 보정본을 더해야 한다.
  - intent 경계 "하지 않는다: 페이지 리사이즈·재인코딩·자동 보정"(intent.md:42).
- **판정에서 검토:**
  - FR-SRV-008(필수) "원본 이미지는 리사이즈·재인코딩 없이 원본 바이트 그대로 전달함을 원칙으로 한다"(prd.md:123). E-67은 서버가 보정본을 **원본 대신** 줄 때만 직접 충돌로 둔다(decisions.md:4289). 확장안은 원본 끝점을 그대로 두고 별도 끝점으로만 주므로 문구상 조건은 피한다. 다만 "원칙"의 예외로 적을지 판정해야 한다. 원본 끝점이 보정본을 주는 순간 직접 충돌이 된다.
  - 최소안과 intent.md:42: 경계의 "자동 보정"이 서버 바이트만 가리키는지 화면 표시까지 가리키는지 문구가 정하지 않는다. 최소안은 서버 바이트를 바꾸지 않으므로 FR-SRV-008·핵심 가치 1과는 충돌하지 않는다. 경계 문구를 "서버의 …"로 좁히는 정리가 필요하다.
  - 확장안: FR-SRV-003(prd.md:118), 보정본의 ETag가 원본과 달라야 함(FR-SRV-007, prd.md:122), CON-001(prd.md:293)과 §6.1 순수 Go 이미지 처리(prd.md:285), NFR-PRF-001 100 ms(prd.md:188)·NFR-PRF-005 유휴 200 MB(prd.md:192). E-67이 설계·검증 조건으로 적은 넷이다(decisions.md:4289).
  - 확장안의 업스케일 품질: 순수 Go로는 보간(이미 있는 `imaging` Lanczos) 수준이고, 학습 모델 기반 업스케일은 WASM 런타임과 모델 파일이 필요해 수 MB 이상이다(추정). 343 902 B 여유를 확실히 넘는다(추정).
  - 최소안: NFR-PRF-002 페이지 전환 즉시(prd.md:189)와 모바일 GPU의 필터 비용(추정). 권별로 기억하려면 FR-VWR-002 권별 설정(prd.md:159)처럼 `book_prefs`(arch-backend.md:764)에 열을 더해야 한다 — 기존 테이블에 열 추가는 이전 규칙(추가는 테이블·인덱스만, arch-backend.md:917-918) 밖이라 새 테이블로 둬야 한다(추정).
