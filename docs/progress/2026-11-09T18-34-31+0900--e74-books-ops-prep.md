### D. cloudflared ingress (sudo. 재시작 순간 **같은 터널의 auth·ohmyassets가 몇 초 끊긴다**. stock·ssh는 다른 터널이라 무관)

```bash

```
기대 출력:
```

PASS  T1    ingress validate                                           OK
PASS  T2    rule https://books.betterax.net/                           -> http://127.0.0.1:9910
PASS  T3    rule https://auth.betterax.net/                            -> https://127.0.0.1:8443
PASS  T4    rule https://ohmyassets.betterax.net/                      -> http://127.0.0.1:18100
PASS  T5    rule https://other.betterax.net/                           -> http_status:404
PASS 5  FAIL 0  WARN 0  SKIP 0
>> rollback: sudo …/tunnel-rollback.sh --backup /etc/cloudflared/config.yml.bak-<UTC> --restart
```
(작업자가 같은 스크립트를 `/etc` 사본에 `--config-path`로 돌린 결과와 같다.) 시간을 골라 재시작:
```bash

journalctl -u cloudflared -n 30 --no-pager | grep -i 'registered tunnel connection'       # 연결 재등록

curl -s -o /dev/null -w '%{http_code}\n' https://ohmyassets.betterax.net/                             # 200
```

수동(스크립트 대신):
```bash

sudoedit /etc/cloudflared/config.yml     # ohmyassets 규칙 뒤, "- service: http_status:404" 앞에 아래 5줄
#  - hostname: books.betterax.net
#    service: http://127.0.0.1:9910
#    originRequest:
#      httpHostHeader: books.betterax.net
#      connectTimeout: 10s
sudo cloudflared tunnel --config /etc/cloudflared/config.yml ingress validate                       # OK
sudo cloudflared tunnel --config /etc/cloudflared/config.yml ingress rule https://books.betterax.net/      # service http://127.0.0.1:9910
sudo cloudflared tunnel --config /etc/cloudflared/config.yml ingress rule https://auth.betterax.net/       # https://127.0.0.1:8443
sudo cloudflared tunnel --config /etc/cloudflared/config.yml ingress rule https://ohmyassets.betterax.net/ # http://127.0.0.1:18100

```
되돌리기(즉시 공개 중단): `sudo $D/tunnel-rollback.sh --backup /etc/cloudflared/config.yml.bak-<UTC> --restart`(수동이면 `sudo cp -p $B /etc/cloudflared/config.yml && sudo systemctl restart cloudflared`). 되돌린 뒤 books는 catch-all 404.

### F. 첫 로그인과 허용 목록

브라우저 경로와 조건:
1. `https://books.betterax.net/` → 서버가 그린 로그인 화면(401) → `uni-auth로 로그인` = `GET /api/auth/oidc/start` → 302 `https://auth.betterax.net/authorize?client_id=zip-viewer&redirect_uri=https://books.betterax.net/api/auth/oidc/callback&code_challenge_method=S256&scope=openid…`. 이때 books가 state 쿠키(`Secure`·`HttpOnly`)를 심는다 — **https로만 동작**한다(`http://IP:9910` 직접 접속으로는 로그인할 수 없다).
2. `auth.betterax.net`에서 로그인(이메일 검증된 계정). uni-auth는 등록된 `redirect_uris`와 **정확히 일치**할 때만 books로 돌려보낸다(U-R3b에서 books 값으로 갱신함).
3. 302 → `https://books.betterax.net/api/auth/oidc/callback?code=…&state=…` → 서버가 state 쿠키와 대조하고, 서버에서 `https://auth.betterax.net/token`으로 코드를 교환한다(호스트 → 공개 터널 경유, 아래 "컨테이너·issuer 경로"). 쿠키를 막는 브라우저 설정·다른 탭에서 시작한 로그인은 state 불일치로 실패한다.
4. 첫 로그인은 **403 화면**이 정상(허용 목록이 비어 있다). 화면의 `sub`를 복사한다.
5. 허용 목록 추가:
   ```bash
   $EDITOR $CFG      # allowed_subs: ["<sub>"], admin_subs: ["<sub>"], legacy_owner_sub: "<sub>"
   kill $(ss -ltnpH "sport = :$PORT" | grep -o 'pid=[0-9]*' | cut -d= -f2); sleep 2
   cd $REPO && nohup dist/shelf --config $CFG >> ~/shelf-books.log 2>&1 &
   ```
6. 다시 로그인 → 서재와 이전 진행률(legacy_owner_sub가 맞으면 한 번 이관, E-74 §2.14).

적용이 끝나면 Orchestrator에 알린다 → U-R3c(공개 검증·독립 검증).
