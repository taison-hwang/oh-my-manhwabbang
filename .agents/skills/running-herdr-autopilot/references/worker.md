# 역할: 워커

Commander·Orchestrator를 뺀 모든 세션이다. `[배정]` 메시지가 임무 정의다.

**모든 턴은 `herdr-report`로 끝낸다.** 화면에 쓴 글은 아무도 읽지 않으므로 보고하지 않으면 전체 진행이 멈춘다. 보고 없이 턴을 끝내려 하면 hook이 막는다.

말머리는 상태 그대로 고른다. Orchestrator는 말머리로 작업의 상태를 판단하므로, 다른 말머리로 대신하거나 `hc send`로 직접 보내면 완료를 잘못 판단한다.

| 상태 | 말머리 |
| --- | --- |
| 배정받은 작업을 커밋까지 끝냈다 | `[완료]` |
| `[병합]`대로 기본 브랜치에 병합했다 | `[병합완료] <작업 ID> <병합한 SHA>` |
| 기다릴 대상이 있어 턴을 끝낸다 | `[진행]` |
| 사용자·외부 결정이나 고칠 수 없는 실패로 막혔다 | `[차단]` |
| Orchestrator의 질문에 답한다(작업 상태는 그대로) | `[답변]` |

- 배정받은 목표·범위 안에서 직접 구현·검증·커밋까지 끝낸다. 서브에이전트는 `SKILL.md`의 "서브에이전트"에 정한 두 경우에만 쓴다.
- 작업을 시작하면 작업 상태 파일을 만들고, 중요한 결정이 생길 때마다 고친다(`managing-session-context` 스킬).
- 코드 변경이면 프로젝트의 검사 명령(`AGENTS.md`, `.agents/harness.env`의 `HERDR_CHECK_CMD`)을 통과시킨다. 파일을 고치면 hook이 그 파일만 빠르게 검사하고, 실패를 돌려주면 그 자리에서 고친다. 독립 리뷰가 필요한 경우(`SKILL.md`의 "서브에이전트")에는 리뷰를 받고 차단 지적을 고쳐 다시 검증한다.
- 전체 테스트·e2e·빌드처럼 무거운 명령을 따로 돌릴 때는 `herdr-queue run --role $HERDR_ROLE -- <명령>`으로 공용 대기열을 거친다. 몇 개 테스트만 고르는 집중 실행은 그대로 돌려도 된다. 대기열 밖의 무거운 실행은 같은 기계의 다른 세션을 메모리 부족으로 죽일 수 있다.
- 다른 세션과 겹치는 파일·인터페이스를 발견하면 고치기 전에 Orchestrator에 알린다.
- 수용 기준을 어떻게 확인할지 알 수 없으면 코드를 쓰기 전에 `[차단]`으로 묻는다.
- 외부 결정이 필요하면 추측하지 않고 `[차단]`으로 묻는다. 기다리는 동안 그 결정과 무관한 일이 남아 있으면 계속한다.
- `[진행]`은 백그라운드 작업이나 다른 세션처럼 기다릴 대상이 있을 때만 보낸다. 지금 할 수 있는 일이 남아 있으면 보고하지 않고 계속한다.
- 인접 기능을 추가하거나 다른 세션의 산출물을 중복 구현하지 않는다.
- 작업을 마치면 `implementing-with-tdd` 스킬의 "완료 근거"를 채우고 커밋까지 한 뒤 작업한 worktree 안에서 `[완료]`를 보고한다. 바꾼 파일(`git diff --stat <분기점>..HEAD`)이 배정 범위 밖이면 보고 전에 되돌리거나 이유를 적는다. 하다가 찾은 범위 밖 수정은 하지 않고 후속 제안으로 적는다. `herdr-report`는 worktree에 커밋 안 된 변경이 있거나 `herdr-check`(전체 검사)가 지금 HEAD에서 실패하면 보내지 않고, 통과하면 `검사 PASS <SHA>`를 붙인다. 검사가 오래 걸리거나 대기열을 기다려야 하면 아래 "검사를 뒤에서 돌리고 다음 작업 쌓기"대로 `herdr-report --bg`로 보낸다. 같은 HEAD에서 통과한 기록이 있으면 보고 때 다시 돌리지 않는다. 고칠 수 없는 실패면 `[차단]`으로 이유를 보낸다. 관문을 피하려고 검사 명령이나 설정을 바꾸지 않는다. 검증은 실행 확인(명령과 결과), 추론, 미확인으로 구분해 적는다. 실행하지 못한 검증은 이유와 미검증 범위를 적고 통과로 표현하지 않는다.
- `[병합]`을 받으면 아래 "병합"을 따른다. 그 위에 쌓은 작업이 있으면 "쌓은 작업이 있을 때 병합"을 따른다.
- 작업 사이에 새 일을 스스로 찾아 시작하지 않는다. 발견한 무관한 문제는 `[완료]`에 한 줄로 적는다.

## 검사를 뒤에서 돌리고 다음 작업 쌓기

검사(공용 대기열 포함)가 끝날 때까지 세션이 놀지 않게 한다. 관문은 그대로다. 병합은 커밋마다 따로 검사 PASS와 판정이 있어야 한다.

- 커밋한 뒤 `herdr-report --bg "[완료] <작업 ID> <요약>"`로 보낸다. 지금 HEAD를 역할별 검사용 worktree에서 검사하므로 이 worktree는 계속 써도 된다. 곧바로 `[진행] <작업 ID> 커밋 <SHA> 검사 중(뒤에서) 예상 … · 대기열 N건`이 가고, PASS면 그 SHA로 `[완료]`가 자동으로 간다. 같은 SHA가 이미 통과했으면 바로 `[완료]`를 보낸다.
- 붙는 예상은 지난 검사 기록의 최대값이다. 이번에 돌 테스트 범위가 평소와 크게 다르면 `[진행] <작업 ID> 커밋 <SHA> 검사 중 예상 <소요 시간>`으로 고친 예상을 보낸다. 수 시간이 걸리면 그대로 적는다.
- 기다리는 동안 같은 묶음의 다음 작업만 그 커밋 위에 쌓아 시작한다. 다른 묶음이나 배정받지 않은 일은 시작하지 않는다. 쌓을 작업이 없으면 턴을 끝낸다. 결과가 오면 다시 깨어난다.
- 검사 중인 커밋은 amend·rebase·reset으로 바꾸지 않는다. 보고한 SHA가 사라지면 그 PASS와 판정을 쓸 수 없다.
- 이 세션에 `[검사 FAIL] <작업 ID> 커밋 <SHA>`가 오면 `[완료]`는 가지 않은 것이다. Orchestrator에는 고치는 중이라고 이미 알렸다. 알림의 로그를 보고 고친다. 위에 쌓은 작업이 있으면 다음 순서로 옮긴다.
  1. 커밋 안 된 변경은 `git stash`로 치운다.
  2. `git branch <작업 ID>-stack`으로 쌓은 커밋을 보관하고 `git reset --hard <실패 SHA>`로 돌아간다.
  3. 고쳐 커밋하고 `herdr-report --bg "[완료] <작업 ID> …"`로 다시 보낸다.
  4. `git cherry-pick <실패 SHA>..<작업 ID>-stack`으로 쌓은 커밋을 다시 올리고, `git stash pop` 뒤 `git branch -D <작업 ID>-stack`로 보관 브랜치를 지운다.

## 병합

판정은 그 SHA의 패치에만 유효하다. rebase로 패치가 바뀌었는지는 기억이나 설명이 아니라 `git patch-id`로 판단한다.

1. rebase 전에 판정 SHA의 패치 값을 적는다: `git diff $(git merge-base <기본 브랜치> <판정 SHA>) <판정 SHA> | git patch-id --stable`
2. 대상 브랜치를 기본 브랜치 최신 상태 위에 올린다(`git rebase <기본 브랜치>`).
3. 같은 방법으로 rebase 뒤 값을 구한다: `git diff <기본 브랜치> HEAD | git patch-id --stable`. 첫 값이 다르면(충돌 해결, 코드 수정, 바로 옆 줄이 바뀐 경우) 병합하지 않는다. 새 SHA와 바뀐 부분을 `[완료]`로 보고하고 새 `[병합]`을 기다린다. 판정이 없는 `[병합]`이면 이 확인은 하지 않는다.
4. 그 SHA에서 `herdr-check`를 통과시킨다. rebase가 아무것도 바꾸지 않아 SHA가 그대로면 이미 PASS 기록이 있어 다시 돌지 않는다.
5. 메인 체크아웃에서 `git merge --ff-only <브랜치>`로 병합한다. 빨리 감기가 안 되면 2부터 다시 한다. 병합 커밋을 만들지 않는다. 검사한 SHA가 곧 기본 브랜치에 들어간 SHA여야 한다.
6. 병합한 worktree는 커밋 안 된 변경이 없는지 확인하고 `git worktree remove`로 지운 뒤 `git branch -d`로 브랜치를 지운다.
7. `herdr-report "[병합완료] <작업 ID> <병합한 SHA> <요약>"`로 보고한다. 그 SHA가 메인 체크아웃 HEAD에 들어 있는지와 검사 PASS 기록을 확인해 붙인다. 검사를 다시 돌리지 않는다. 기록이 없으면 그 SHA를 뒤에서 검사한 뒤 보낸다.

메인 체크아웃에서 `[완료]`를 보내지 않는다. 그곳에는 다른 세션의 변경이 섞여 있다. 보내면 `herdr-report`가 커밋된 HEAD만 보고, PASS 기록이 없으면 그 자리 대신 검사용 worktree에서 검사한다.

### 쌓은 작업이 있을 때 병합

`[병합]`에 적힌 SHA까지만 병합한다. 쌓은 커밋은 아직 검사·판정을 받지 않았다.

1. 커밋 안 된 변경을 `git stash`로 치우고 `git switch -c <작업 ID>-merge <SHA>`로 그 SHA에서 가른다.
2. 이 브랜치를 위 "병합" 절차대로 기본 브랜치 위에 올려 검사하고 병합한다. 패치 값이 다르면 같은 절차대로 멈추고 보고한다.
3. 작업 브랜치로 돌아와 `git rebase <기본 브랜치>`로 쌓은 작업을 옮긴다. 이미 병합된 커밋은 rebase가 건너뛴다. `git stash pop` 뒤 `<작업 ID>-merge`를 지운다.
4. worktree와 작업 브랜치는 쌓은 작업이 끝날 때까지 지우지 않는다. 병합 결과는 `[병합완료]`로 보고한다.

## `[검증]`을 받았을 때

판정만 한다. 제품 코드를 고치거나 커밋하지 않는다.

```bash
git worktree add --detach docs/.worktrees/verify-<묶음> <head SHA>
```

- 작업은 그 worktree에서 한다. 재현에 필요한 파일은 그 안에 임시로 만들고 커밋하지 않는다.
- 커밋 메시지, 주석, 문서의 설명을 근거로 삼지 않는다. 수용 기준마다 실제로 실행하거나 코드를 읽어 확인한다.
- 사용자가 쓰는 경로를 실행한다. 테스트 통과만으로 기능이 동작한다고 판정하지 않는다.
- 변경 범위는 `git diff <분기점 SHA> <head SHA>`로 본다. 움직이는 `main`과 비교하면 다른 커밋이 섞인다.
- 찾은 문제를 "사소하다"고 스스로 넘기지 않고 `SKILL.md`의 "차단 기준"으로 나눈다.
- 메인 체크아웃에 `docs/progress/<타임스탬프>--verify-<묶음>.md`(`type: review`)를 쓴다. 기준별 결과, 실행한 명령과 출력, 차단 결함, 후속 제안을 적는다. 커밋은 Orchestrator가 한다.
- worktree를 지우고 `herdr-report "[판정] <묶음> PASS|ISSUES|BLOCKED <head SHA> <기록 경로>"`로 보고한다. `BLOCKED`는 실행할 수 없었던 이유를 기록에 적은 경우다.
