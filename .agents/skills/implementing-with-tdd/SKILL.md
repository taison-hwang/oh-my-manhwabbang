# 구현

테스트가 실행 가능한 명세다. 구현 상세의 진실은 최신의 검증된 코드와 테스트이고, 코드의 동작·분기·자료구조를 문서에 옮기지 않는다.

명령은 프로젝트가 정한다: 테스트·전체 검사는 `AGENTS.md`의 "검사 명령", 뮤테이션은 "뮤테이션". 이 스킬은 도구를 정하지 않는다.

## 코드를 쓰기 전에

- 데이터 모양을 먼저 정한다. 핵심 타입과 자료구조를 정하고, 어떤 경로로 읽히고 바뀌는지 따라가 본 뒤 로직을 쓴다.
- 분기 대신 구조로 담는다: 흩어진 boolean·단계 검사 대신 상태 기계, 반복되는 모양 가정 대신 타입 모델, 여러 파일에 퍼진 if/else 대신 표·등록부·판별 유니언. 새 기능이 기존 if/else 사슬에 가지 하나를 더하거나, 서로 맞춰야 하는 두 번째 boolean이 생기면 구조가 빠진 것이다. 지금 모양이 분명하고 자랄 일이 없으면 단순한 코드를 둔다.
- 함수 경계를 넘는 코드는 호출하는 쪽의 사용 예를 먼저 쓰고, 거기서 타입과 시그니처를 정한다. 되돌리기 어려운 설계면 구조가 다른 안을 둘 이상 그려 비교한 뒤 고른다.
- 검증·오류 처리는 시스템 경계(CLI 인자, 설정, 네트워크, 외부 API, DB 행)에 모은다. 경계에서 파싱해 타입으로 만들고, 안쪽에서는 다시 검사하지 않는다. 업무 로직은 프레임워크에 묶이지 않는 순수 함수로 둔다.
- 상태를 바꾸는 작업은 두 번 돌려도, 중간에 죽은 뒤 다시 돌려도 같은 결과가 나게 한다. 남긴 잠금·임시 파일·반쯤 쓴 기록은 다음 실행이 낡은 것으로 알아볼 수 있어야 한다.
- 여러 실행 주체가 같은 파일·키·브랜치를 쓰게 되면 먼저 공유를 없앤다(주체마다 자기 것을 쓰고 읽을 때 합친다). 하나의 쓰기 대상이 정말 필요할 때만 잠금·순차 단계·단일 쓰기 주체로 구조적으로 막는다. 규칙 문구는 동시성 제어가 아니다.
- 아래 설계 신호가 보이면 모양을 고친다.

| 신호 | 고치는 방향 |
| --- | --- |
| 한 작업에 호출자가 메서드 여러 개를 맞춰 불러야 한다 | 작은 인터페이스 뒤에 동작을 모은다 |
| 같은 내부 결정(표현, 정책, 형식)이 여러 모듈에 나온다 | 한 모듈이 갖고 나머지는 그 모듈의 타입을 쓴다 |
| 모듈이 실행 순서(읽기, 검증, 변환, 저장)로 나뉘어 같은 규칙을 반복한다 | 지식과 소유권 기준으로 묶는다 |
| 같은 인자를 그대로 넘기기만 하는 층 | 지운다 |
| 같은 상태를 여러 모듈이 쓰거나 사본을 갖는다 | 소유자를 하나로 정한다 |
| 같은 일을 하는 방법이 둘이다 | 하나만 남기고 호출처를 옮겨 나머지를 같은 변경에서 지운다 |
| 같은 목록을 여러 곳에서 손으로 맞춘다 | 하나에서 만들어 쓰거나, 어긋나면 빌드가 실패하게 한다 |

## TDD 대상

- 대상: 도메인 규칙, 서버·API, 변환·오류 처리, 데이터 검증, 렌더링·내보내기, 화면 상태·상호작용.
- 제외: 설정, 골격, 문서, 기계적 생성 코드. 제외 대상은 위험에 비례해 검증한다.

## 절차

테스트 하나 단위로 반복한다.

```
TDD 진행:
- [ ] 1. 요구사항·외부 계약에서 기대값을 정했다
- [ ] 2. 실패하는 테스트를 작성·실행해 의도한 이유로 실패하는 것을 확인했다
- [ ] 3. 그 테스트를 통과시키는 최소 구현을 했다
- [ ] 4. 관련 테스트가 통과한다
- [ ] 5. 리팩터링 후 관련 테스트와 바뀐 파일의 lint·타입 검사가 다시 통과한다
- [ ] 6. [완료] 보고 전에 "뮤테이션 확인"과 "완료 근거"를 처리했다
```

- 편집 직후 빠른 검사는 hook이, 전체 검사는 [완료] 보고 때 `herdr-report` 관문이 돌린다. role이 없는 단일 세션은 끝내기 전에 `.agents/bin/herdr-check`를 직접 돌린다.
- 관련 테스트(4·5단계)는 프로젝트 hook이 맡지 않으면 검사 명령으로 직접 돌린다. 매 실패·통과 사이클마다 전체 검사를 돌리지 않는다.
- 2단계에서 테스트가 통과하거나 엉뚱한 이유로 실패하면 구현을 고치기 전에 테스트나 재현을 고친다.
- 일부러 실패 상태로 턴을 끝낼 때(실패 테스트만 쓰는 단계를 맡은 경우)는 보고에 그 사실과 실패 내용을 적는다.
- 검사 실패는 고친 뒤 진행한다. lint 규칙을 끄거나 무시 주석을 달 때는 그 자리에 이유를 남긴다. hook이나 관문을 건너뛰지 않는다.
- 작은 단위마다 확인하고 다음으로 간다. 확인 안 된 변경 위에 쌓지 않는다. 커밋은 하나의 목적만 담고, 순서가 그대로 근거가 되게 쌓는다(지우기 → 구조 바꾸기 → 기능, 기준 측정 → 개선).

## 작업 종류별

### 기능

- 바꿀 하위 시스템을 먼저 읽고(호출 관계, 데이터 흐름), 위 "코드를 쓰기 전에"로 모양을 정한 뒤 쓴다.
- 지울 것(죽은 코드, 쓰지 않는 검증, 남은 참조)을 먼저 지우고 그 위에 만든다.
- 수용 기준에 없는 인접 기능, 설정 옵션, 추측성 가드는 넣지 않는다.

### 버그 수정

- 실제 경로에서 먼저 재현한다. 재현이 안 되면 조건을 좁히거나 계측(로그, 상태 출력)을 넣어 일어나게 만든다. 추측으로 고치지 않는다.
- 후보 가설을 적고, 실행 증거로 하나씩 지운다. 남은 원인의 동작을 실행 증거로 확인한 뒤 고친다.
- 원인은 증상이 보인 곳이 아니라 처음 잘못된 곳이다. 그 상태가 정상적으로 있을 수 있으면 그 상태에서 깨진 코드가 원인이다. 있으면 안 되는 상태면 그 상태를 만든 곳을 찾는다. 가드, 재시도, 오류 삼키기, 값 자르기로 증상을 덮지 않는다.
- 재시작 뒤에만 실패하면 저장된 상태(설정, 캐시, 잠금 파일, 직렬화된 상태)부터 의심한다.
- 같은 결함이 다른 곳에도 있는지 찾아 함께 고친다.
- 반증된 가설로 넣은 변경은 되돌린다. "혹시 몰라" 넣은 수정은 남기지 않는다.
- 같은 전제를 가진 수정이 두 번 실패하면 세 번째 수정을 쓰기 전에 그 전제를 한 문장으로 적고, 전제가 틀리면 결과가 달라질 관찰을 먼저 해 본다.
- 원인을 찾는 데 오래 걸렸으면 다음에 바로 보였을 신호(로그, 검사)를 후속 제안으로 적는다.

### 리팩터링

동작은 그대로 두고 구조만 바꾼다.

- 구조를 옮기기 전에 지금 동작을 고정한다: 특성 테스트, 스냅샷, 전·후 출력을 비교하는 스크립트. 덮는 테스트가 없으면 고정부터 쓴다. 타입 검사와 lint는 고정이 아니다.
- 목표 모양을 적는다: 지금 새로 만든다면 모듈 배치, 타입, 호출 관계가 어떠해야 하는가. 바꾼 모양은 분기나 불가능한 상태를 지워야 한다. 층만 늘리면 하지 않는다.
- 지우기 먼저: 죽은 코드, 호출처 하나뿐인 래퍼, 중복 검증, 끊긴 참조.
- 작은 단계로 옮기고 단계마다 고정이 통과하는지 본다.
- API를 바꾸면 호출처를 모두 옮기고 옛 API를 같은 작업에서 지운다. 외부 사용자가 없으면 호환 계층이나 옛 경로·새 경로 병행을 남기지 않는다.
- 이름 바꾸기는 코드 밖 사용처(문자열, 문서, 설정, 다른 언어)까지 검색해 확인한다.
- 리팩터링 중 찾은 버그나 빠진 기능은 같은 커밋에 섞지 않고 따로 고치거나 후속으로 적는다.
- 끝나고 읽는 사람의 부담이 줄었는지 본다: "X가 어디서 오나", "무엇이 X를 바꾸나"에 바로 답할 수 있는가. 줄지 않았으면 되돌린다.

### 공유 코드를 바꿀 때

공유 함수, 스키마, 설정, 직렬화 형식, 공용 타입을 바꾸면 다른 곳이 깨질 수 있다.

- 호출처뿐 아니라 검색이 놓치는 곳을 본다: 그 값을 읽는 다른 언어·서비스, DB 컬럼, API 응답 형식, 기능 플래그, 몇 단계 아래의 소비자.
- 변경이 안전하다는 근거가 되는 사실 하나를 찾아 실행으로 확인한다(실제 코드를 부르는 작은 스크립트나 테스트). 확인하지 못했으면 보고에 미확인으로 적는다.

### 반복 편집

- 같은 모양의 편집이 많으면 첫 단위를 손으로 한 뒤 스크립트(코드모드, 생성기)로 만든다. 그 스크립트를 첫 단위에 다시 돌려 손으로 한 결과와 같은지 본 뒤 나머지에 돌린다. 스크립트는 다시 돌려도 안전하게 만들고, 작업이 이 세션보다 오래 가면 커밋한다.
- 확인도 다시 돌릴 수 있는 스크립트로 만든다.

## 뮤테이션 확인

- `AGENTS.md`에 뮤테이션 명령이 없으면 하지 않고 보고에 "뮤테이션 미설정"을 적는다.
- 분기·경계 조건이나 도메인·상태 로직을 바꿨으면 [완료] 보고 전에 실행한다. 그 밖에는 생략하고 보고에 "뮤테이션 생략(분기 변경 없음)"을 적는다. 프로젝트가 범위를 정했으면 그것을 따른다.
- 점수 임계값으로 막지 않는다. 생존 변이마다 판단한다: 동작이 실제로 달라지는 변이(경계값·분기)면 그 경우를 드러내는 테스트를 추가하고, 동등 변이나 의미 없는 문구 변이는 넘긴다.
- 보고에 변이 생성·잡힘·생존 수와 처리한 생존 변이를 적는다.

## 테스트 작성 규칙

- 테스트는 사용자(호출자, 최종 사용자, 다른 서비스)가 관찰하는 동작을 단언한다: 반환값, 호출자가 분기하는 오류 종류, 다시 읽을 수 있는 상태, 외부로 나간 요청·기록·메시지.
- 두 가지 가상 편집으로 테스트를 본다. 동작을 깨면(틀린 값, 효과 생략, 효과 두 번) 실패해야 하고, 관찰 결과를 그대로 두고 내부만 바꾸면 통과해야 한다. 내부 helper 호출, 내부 호출 순서, 중간 데이터, 호출자가 읽지 않는 오류 문구는 단언하지 않는다.
- 구현을 돌려 나온 값을 기대값으로 옮겨 적지 않는다. 기대값은 요구사항에서 정한다.
- 테스트가 직접 만든 데이터만 확인하는 단언, 계약보다 느슨한 단언은 아무것도 증명하지 않는다.
- 버그 수정은 그 버그를 재현하는 실패 테스트부터 쓴다.
- 실패 경로·입력 검증·오류·경계·회귀 위험을 테스트한다.
- 나쁜 테스트보다 테스트가 없는 편이 낫다. mock만 시험하거나, 타이밍·무관한 전역 상태에 기대거나, 작은 수정에 큰 인프라가 드는 테스트는 쓰지 않는다. 대신 가장 가까운 실행 확인(재현 명령, 스크립트, 화면 자동화)을 쓰고 이유와 함께 보고한다.
- 틀린 구현에 맞추려고 테스트를 고치거나 기존 단언을 약하게 하지 않는다. 기대 동작이 정말 바뀐 경우에만 이유를 적고 고친다.
- 플레이크는 결정적으로 만들 수 있으면 그렇게 고치고, 고정하려는 신호를 테스트 이름에 드러낸다.
- 테스트 이름은 검증하는 규칙을 문장으로 드러낸다.

## 완료 근거

완료는 수용 기준을 실제 대상에서 확인한 상태다. "컴파일된다", 검사 PASS, 자기 설명은 완료 근거가 아니다. 검사 PASS는 관문일 뿐이다.

| 바꾼 것 | 확인 |
| --- | --- |
| CLI·스크립트 | 그 명령을 실제 입력으로 실행 |
| 화면 | 실행 중인 앱에서 바뀐 흐름을 끝까지 조작 |
| API·서버 | 띄운 서버에 실제 요청 |
| 파서·변환·마이그레이션 | 저장한 실제 입력을 다시 돌림 |
| 저장 | 쓴 값을 다시 읽음 |
| 성능 | 같은 조건에서 전·후를 여러 번 재고 반복 수, 범위, 제한 요인(무엇이 더 빠르지 못하게 막는가)을 적음 |
