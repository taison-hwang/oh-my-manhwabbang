# 문서 작성

문서는 개발의 방향타와 체크리스트다. 상세는 코드와 테스트가 맡는다.

목차: 무엇을 쓰는가 · 문서 종류 · 읽기 · 개발 과정 기록 · 최신성 판단 · 작업 계획과 상태판 · 문장

## 무엇을 쓰는가

- 쓴다: 목표·범위·비목표, 제약, 외부 계약, 핵심 결정과 이유, 기능별 수용 기준, 운영 절차.
- 쓰지 않는다: 코드의 동작·API 세부·분기·자료구조, 코드와 함께 자주 바뀌는 상세. 상세가 필요하면 코드·테스트 경로를 가리킨다.
- 한 사실은 한 곳에만 두고 나머지는 링크한다.

## 문서 종류

| 종류 | 위치 | 수정 규칙 |
| --- | --- | --- |
| 의도 요약 | `intent.md` | 목적·대상·핵심 가치·승인·경계를 한 화면으로. 상세는 서비스 기획을 링크한다. 사용자 승인 후 고친다 |
| 서비스 기획 | `docs/service-plan/` | 무엇을 왜 만드는가. 기술 내용은 두지 않고 설계를 링크한다. 구현을 막는 결함만 고친다 |
| 설계 | `docs/design/` | 어떻게 만드는가. 구현을 막는 결함만 고친다 |
| 개발 과정 기록 | `docs/progress/` | 결정·조사·경과·리뷰·차단 요인·완료 근거. 새 파일로만 추가하고 기존 파일은 고치거나 지우지 않는다 |
| 현재 상태 | `docs/status/` | 작업 계획과 상태판. 최신 내용으로 고쳐 쓴다 |

## 읽기

필요한 것만 연다.

- 처음에는 `intent.md`로 프로젝트의 본질을 확인한다.
- `docs/service-plan`·`docs/design`·`docs/status`는 `index.md`부터 읽고 목차의 "언제 읽는가"에 맞는 문서만 연다. 문서를 나누거나 `index.md`를 고칠 때의 형식·절차·검증은 [references/splitting-and-indexing.md](references/splitting-and-indexing.md)를 따른다.
- `docs/progress`는 필요한 주제 키의 최신 기록만 연다. 이전 기록은 `supersedes`가 가리키거나 경과가 필요할 때만 연다.

## 개발 과정 기록

- 파일명: `<타임스탬프>--<주제-키>.md`. 타임스탬프는 `date '+%Y-%m-%dT%H-%M-%S%z'`로 만든다. 이름순 정렬이 곧 시간순이다.
- 주제 키: 같은 주제를 이어 쓰면 그대로 재사용한다. 새로 만들기 전에 찾는다: `ls docs/progress | grep -- '--<키워드>'`. 최신 기록: `ls docs/progress | grep -- '--<주제-키>\.md$' | tail -1`.
- 본문 맨 앞 메타데이터(시각은 `date -Iseconds`):

  ```
  timestamp: 2026-10-31T19:30:00+09:00
  topic: jd-parser-schema
  type: decision | investigation | progress | review | blocker | snapshot
  status: proposed | accepted | done | blocked
  supersedes: docs/progress/<이전 파일>   # 정정·대체할 때만
  ```

- 본문: 결론, 근거, 영향, 다음 행동만 쓴다.

## 최신성 판단

- 같은 주제 키의 기록이 충돌하면 타임스탬프가 가장 최근인 기록이 우선한다. 대체할 때는 `supersedes`와 바꾼 이유를 쓴다.
- 방향 문서보다 최근의 결정 기록은 해당 부분에서 방향 문서보다 우선한다. 결정이 쌓이면 사용자 승인을 받아 방향 문서에 반영하고 그 사실을 새 기록으로 남긴다.
- 이 원칙은 문서끼리의 판단에만 쓴다. 실제 동작은 검증된 최신 코드·테스트가 기준이다. 기록과 코드가 다르면 차이를 새 기록으로 남긴다.
- 에이전트의 기록은 사용자 결정을 뒤집지 못한다. 다른 내용을 쓰려면 사용자 승인 근거(일시·내용)를 함께 적는다.
- 한 주제의 기록이 쌓여 현재 상태를 알기 어려우면 `type: snapshot`으로 결론을 정리하고 반영한 기록을 `supersedes`에 나열한다.

## 작업 계획과 상태판

Orchestrator가 고쳐 쓴다. 재개할 때는 `work-plan.md` → `status-board.md` 순서로 읽는다.

| 문서 | 내용 |
| --- | --- |
| `docs/status/work-plan.md` | 진행·대기 작업만. 작업마다 ID, 의존 묶음, 수용 기준(행동과 확인 방법), 의존 작업, 바꿀 파일·모듈 |
| `docs/status/status-board.md` | 작업 표 하나와 미확정 사항 |
| `docs/status/completed.md` | 끝난 행을 옮겨 두는 기록. 새 행을 아래에 추가한다 |
| `docs/status/decisions.tsv` | 결정 한 줄 기록. 새 줄만 추가한다. 형식은 `running-herdr-autopilot`의 `references/orchestrator.md` |

- 두 문서 맨 위의 `갱신: <date -Iseconds>`를 고칠 때마다 바꾼다.
- 상태 값은 `대기`, `진행`, `리뷰`, `완료`, `차단`이다. `완료`는 검증 근거가 있을 때만 쓴다.
- 상태판의 근거 칸에는 링크·커밋·검사 결과 요약만 약 200자 이내로 쓴다. 상태판은 자주 다시 읽히므로 길이가 곧 비용이다. 긴 내용은 `docs/progress/`에 기록하고 링크한다.
- 끝난 행은 묶음을 마칠 때 `completed.md`로 옮긴다.
- 상태판 고치는 시점: 묶음을 시작·종료할 때, 차단이 생기거나 풀릴 때, 정리를 요청하기 직전, 사용자에게 보고할 때.

## 문장

- 바로 실행할 수 있게 쓴다: 조건 → 행동 순서, 구체적인 경로·명령·값.
- "적절히", "필요시"처럼 판단 기준이 없는 표현은 기준을 함께 쓴다.
- 날짜가 지나면 틀려질 문장("현재", "최근")은 쓰지 않고 날짜를 적는다.
